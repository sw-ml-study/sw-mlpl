Every math line below is rendered by MLPL itself: the svg(text, "equation") builtin turns a line of Unicode math into a self-contained SVG, embedded inline in this page – no LaTeX toolchain, no MathJax, no network. Every code block is a live MLPL source block, evaluated top-to-bottom in one shared :session cnn.

1. The equation

Zhao, Wang, Wang & Liu (2018), section 2.1, define an output pixel of a convolution as a weighted sum over the Q input channels and the Mw x Nw kernel window, for each of R output filters. Rendered from MLPL, with the paper's bounds intact: 

svg("y[r,x,y] = ∑_{q=1}^{Q} ∑_{u=1}^{Mw} ∑_{v=1}^{Nw} W[r,q,u,v] · X[q, x+u, y+v]", "equation")

Read it as: for output filter r at position (x, y), sum over every input channel q = 1..Q and every kernel offset u = 1..Mw, v = 1..Nw the weight W[r,q,u,v] times the shifted input X[q, x+u, y+v]. Every sum is finite and every bound is a dimension of one of the two arrays – the first hint that this loop notation is really an array operation. One caveat when transcribing it into code: the paper counts from 1 and the array language from 0, so q = 1..Q becomes channels 0..Q-1, and the reduction axis numbers below are 0-based too. The rest of this page writes the triple sum with no explicit loops.

2. Receptive fields: windows

The inner object is the receptive field – the little patch of the input that one output pixel sees. windows extracts every receptive field at once. For a [channel, height, width] input and a [kernel_y, kernel_x] window, it returns a [out_y, out_x, channel, kernel_y, kernel_x] tensor: the leading axes index the output grid, and the trailing [channel, kernel_y, kernel_x] block is exactly the receptive field at that position. 

image = reshape(range(16) + 1, [1, 4, 4])   # one channel, a 4x4 ramp
shape(windows(image, [3, 3]))                # [out_y, out_x, channel, kernel_y, kernel_x]

2 2 1 3 3

That axis order is the load-bearing choice: the receptive field sits in the trailing axes, so a flattened kernel will line up with it by position, with no transpose.

3. im2col: flatten the fields into columns

Stack the output grid into rows and flatten each receptive field into a column. That is the classic im2col rearrangement – one row per output pixel, one column entry per (channel, kernely, kernelx): 

svg("cols[i, :] = flatten( field_i ),   i over the out_y·out_x pixels", "equation")

patches = windows(image, [3, 3])
ps = shape(patches)
cols = reshape(patches, [take(ps, 0, 0) * take(ps, 0, 1), 1 * 3 * 3])
shape(cols)                                  # [out_y*out_x, channel*kernel_y*kernel_x]

4. The contraction: one matmul

Now the triple sum ∑_q ∑_u ∑_v is just a dot product between each column and the flattened kernel – and doing all pixels at once is a single matrix multiply: 

svg("y = cols · flatten(W)          (one matmul contracts every receptive field)", "equation")

Putting it together as a reusable function: 

def u:conv_im2col(x, kernel) {
  "im2col convolution: windows stacks each receptive field, reshape flattens them into columns, and one matmul contracts every column against the flattened kernel -- the whole convolution as a single matrix multiply, no loops and no rank broadcasting"
  ks = shape(kernel)
  kh = take(ks, 0, 1)
  kw = take(ks, 0, 2)
  patches = windows(x, [kh, kw])
  ps = shape(patches)
  out_h = take(ps, 0, 0)
  out_w = take(ps, 0, 1)
  cols = reshape(patches, [out_h * out_w, tally(flatten(kernel))])
  reshape(matmul(cols, flatten(kernel)), [out_h, out_w])
}

5. A worked example: a vertical-edge filter

Convolve the 4x4 ramp with a vertical-edge kernel. The ramp's horizontal gradient is constant, so every valid output position is the same value: 

edge = reshape([1, 0, -1, 1, 0, -1, 1, 0, -1], [1, 3, 3])   # a vertical-edge filter
u:conv_im2col(image, edge)                                   # -6 everywhere

6. Multiple input channels

The channel sum ∑_q is not special: flatten(kernel) spans all channels, so the same one-line matmul contracts across them. Two input channels, one filter, checked against the oracle to the last bit: 

x2 = reshape(range(50) + 1, [2, 5, 5])                       # two channels, 5x5
k2 = reshape(range(8), [2, 2, 2])                            # one filter over both channels
mine = u:conv_im2col(x2, k2)
oracle = reshape(conv2d(reshape(x2, [1, 2, 5, 5]), reshape(k2, [1, 2, 2, 2]), 1, 0), [4, 4])
reduce(:max, abs(mine - oracle))                             # 0 -- exact parity

0

The equation and the code now say the same thing: a convolution is a weighted sum over each receptive field, and MLPL writes that sum as windows then reshape then one matmul.

And it is not just runnable but LEARNABLE. Every op in the forward pass has a tape backward – windows scatter-adds each output gradient onto the input positions its window covered, the reduce broadcasts its gradient back, and the kernel multiply broadcasts (and un-broadcasts on the way back). So grad(loss, kernel) is exact and a kernel can be learned by gradient descent: give the kernel a target and minimise the squared error, and adam recovers it to machine precision. A convolution here is a full trainable layer, built from array primitives with no conv-specific autograd.
