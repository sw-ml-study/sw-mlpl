the existing CPU interpreter/native runtime,

This is highly feasible as a correctness-first feature. It is moderately difficult as a performant accelerator feature, because mHC itself is mathematically simple, but it exposes architectural weaknesses in the current backend boundary—especially MLX graph fragmentation and CPU-based autograd.

The encouraging point is that your existing projects already contain nearly all the conceptual pieces:

DeepSeek presents mHC as a general projection of HC connectivity onto a constrained manifold, not as a CUDA-specific algorithm. 

My recommendation is to treat mHC as two related language capabilities, not one monolithic built-in:

General constrained tensor transformations

A high-level multi-stream residual model layer

That separation will make mHC a useful language feature rather than a one-off demo.

1. What mHC requires
Your POC represents hidden state as:

[batch, tokens, streams, features]
For each model layer, it performs approximately:

x_pre     = mix(H_pre, x)
merged    = mean(x_pre, stream)
f_out     = block(merged)
f_streams = broadcast(f_out, stream)
f_mixed   = mix(transpose(H_post), f_streams)
residual  = mix(H_res, x)
x_next    = residual + f_mixed
Here:

H_pre is row-stochastic.

H_post is row-stochastic.

H_res is doubly stochastic.

H_res is produced by exponentiating learned logits and applying repeated row/column normalization.

That is precisely how your current MLX reference model is structured.

The doubly stochastic projection is:

X = exp(logits)

repeat iterations:
    X = X / max(sum(X, rows), epsilon)
    X = X / max(sum(X, columns), epsilon)
Your MLX and PyTorch implementations deliberately mirror each other.

This is computationally modest because the stream matrix is normally very small—often 4 × 4. The expensive work remains the transformer block, not Sinkhorn itself.

2. Feasibility by backend
Target	Correctness feasibility	Performance feasibility	Main risk
CPU interpreter	Very high	Adequate for demos	Deep interpreter overhead
Compiled CPU	Very high	Good for small models	Temporary tensor allocations
MLX current architecture	High	Initially poor/modest	Per-op conversion and forced evaluation
MLX fused/native graph	High	Good	Requires graph-level lowering
CUDA via Rust tensor library	High	Good	Backend/library choice
CUDA custom kernels	Unnecessary initially	Potentially excellent	Large maintenance cost
WASM	High for visualization/small demos	Poor for deep training	Memory and execution time
CPU
CPU-only mHC should be your first implementation target.

The Sinkhorn matrix is tiny, and the stream mixing can be implemented using existing reshape/transpose/matmul operations. Even a 48-layer synthetic stress test should be practical at small dimensions.

CPU gives you:

deterministic reference behavior,

straightforward finite-difference gradient checks,

no device transfer complications,

WASM-compatible educational demos,

a reference oracle for MLX and CUDA parity tests.

The main CPU optimization is not a special Sinkhorn implementation. It is avoiding repeated allocation and general-purpose tensor dispatch inside every layer.

MLX
Correctness is very feasible, but the current MLX backend is not yet shaped for efficient mHC training.

Your MLX documentation identifies four existing bottlenecks:

f64-to-f32 and f32-to-f64 copies on every operation,

an .eval() after each primitive,

CPU tape construction followed by MLX rematerialization,

workloads too small to amortize accelerator overhead.

mHC would magnify the first three because every layer introduces:

multiple reductions,

normalizations,

transposes,

small matrix multiplications,

broadcasting,

and repeated Sinkhorn iterations.

A literal interpreter-level implementation of 20 Sinkhorn iterations could generate dozens of backend crossings per layer. It would be correct but probably slower than CPU.

Therefore:

Implement mHC on the current MLX path for parity first, but do not use its initial speed as evidence about MLX’s suitability.

The real MLX target should lower the entire Sinkhorn projection—or preferably the entire mHC layer—as a lazy MLX graph before evaluation.

CUDA
CUDA is feasible through several paths, but I would avoid writing custom CUDA kernels first.

The POC proves that ordinary PyTorch operations are sufficient to reproduce the MLX behavior. Your CUDA reference uses standard differentiable tensor operators rather than a specialized Sinkhorn kernel.

For sw-MLPL, the practical choices are:

Approach	Benefits	Risks
candle-core CUDA backend	Rust-native, relatively lightweight	Operator/autograd coverage may require additions
burn backend	Multi-backend architecture and training abstractions	More framework policy than MLPL may want
tch-rs/LibTorch	Mature CUDA and autograd	Large dependency, C++ runtime, deployment complexity
cudarc + custom runtime	Maximum control	You must build tensor ops and autograd plumbing
External PyTorch worker	Fastest experiment	Violates the long-term no-Python deployment goal
For the first CUDA backend, I would lean toward Candle or Burn as an execution substrate, hidden below your own backend traits. Do not let either framework’s model API leak into MLPL.

3. Recommended language design
Layer 1: General tensor primitive
Add a general operation:

H = sinkhorn(logits,
             iterations=20,
             epsilon=1e-12,
             axis_rows="out_stream",
             axis_cols="in_stream")
A more general name might be:

H = doubly_stochastic(logits, iterations=20)
I prefer doubly_stochastic as the user-facing operation and sinkhorn as an optional lower-level primitive:

H = doubly_stochastic(logits)
H = sinkhorn(exp(logits), iterations=20)
Semantics should state explicitly:

logits are transformed to positive values first,

normalization runs for a fixed number of iterations,

output approximately satisfies row and column sums of one,

gradients flow through every iteration,

computation occurs in at least fp32 even under lower-precision training.

Why expose this separately?
It provides reusable support for:

mHC,

differentiable assignment,

transport-like models,

routing matrices,

mixture balancing,

permutation relaxations,

attention constraints.

It also makes the mHC demo educational: users can inspect the actual constrained matrix.

Layer 2: Stream mixing layer
Add:

mix = stream_mix(
    streams=4,
    constraint="doubly_stochastic",
    sinkhorn_iterations=20,
    init="near_identity"
)
Application:

y = apply(mix, x)
With labeled dimensions:

x : [batch, token, stream, feature]
H : [out_stream, in_stream]
y = stream_matmul(H, x, axis="stream")
A dedicated stream_matmul operation is useful even if it lowers to transpose + matmul + transpose. It preserves intent, validates labels, and gives accelerator backends an optimization target.

Layer 3: High-level mHC wrapper
Provide a compositional model layer:

block = mhc(
    transformer_block(...),
    streams=4,
    sinkhorn_iterations=20
)
Then:

model = chain(
    embed(vocab, width),
    repeat_layer(
        mhc(
            transformer_block(width, heads, ff_width),
            streams=4
        ),
        depth=48
    ),
    collapse_streams("mean"),
    rms_norm(width),
    linear(width, vocab)
)
Alternatively, explicitly represent the stream expansion:

model = chain(
    embed(vocab, width),
    expand_streams(4),
    repeat_layer(mhc_block(...), 48),
    reduce_streams("mean"),
    rms_norm(width),
    linear(width, vocab)
)
I favor the second form because the tensor topology remains visible.

4. Do not hard-code mHC as “a Transformer feature”
mHC should wrap an arbitrary model component:

mhc_block(mlp(...))
mhc_block(attention(...))
mhc_block(conv_block(...))
mhc_block(state_space_block(...))
The DeepSeek paper describes mHC as a generalized connection architecture intended to restore desirable residual identity behavior while preserving richer HC connectivity. 

Your internal representation should therefore resemble:

pub struct MhcLayer {
    body: ModelId,
    streams: usize,
    pre_mix: StreamMix,
    post_mix: StreamMix,
    residual_mix: StreamMix,
    collapse: StreamCollapse,
}
Not:

pub struct MhcTransformerLayer { ... }
A transformer demo can be the flagship use case, but the runtime abstraction should remain model-independent.

5. Backend architecture
The important architectural decision is to stop implementing complex model operations solely as sequences of evaluator-level primitive calls.

Use three lowering levels.

Level A: Language AST
MhcLayer
DoublyStochastic
StreamMix
ExpandStreams
ReduceStreams
These retain user intent, labels, validation rules, and documentation.

Level B: Backend-neutral tensor IR
For example:

Exp
ReduceSum
MaximumScalar
Divide
Transpose
MatMul
Broadcast
Add
Mean
LoopFixed
Initially, DoublyStochastic can lower to these primitives.

Later, preserve it as a composite IR node:

DoublyStochastic {
    input,
    iterations,
    epsilon,
}
That allows backend fusion.

Level C: Backend-specific execution
CPU: optimized Rust loops or general tensor primitives.

MLX: construct one lazy MLX graph and evaluate at a materialization boundary.

CUDA: invoke backend tensor operations or a fused implementation.

WASM: scalar/SIMD CPU implementation.

This structure prevents the interpreter from becoming the execution engine for accelerators.

6. Autograd design
Initial approach
Allow the current reverse-mode tape to record Sinkhorn as ordinary differentiable operations:

exp
sum
maximum
divide
This is the easiest correctness path and should work on CPU immediately.

Tests should include:

finite-difference checking of logits,

gradient comparison against the MLX POC,

gradient comparison against the PyTorch POC,

checks near the epsilon clamp boundary,

tests with identity-like and random initialization.

Better approach
Add a composite tape node:

TapeOp::DoublyStochastic {
    input: NodeId,
    iterations: u16,
    epsilon: f32,
}
There are two ways to backpropagate it:

Option A: Save every iteration
Pros

simplest mathematically,

closely follows ordinary autograd,

easy to validate.

Cons

memory grows with Sinkhorn iteration count,

duplicates many tiny intermediate matrices.

For stream count four and 20 iterations, this memory is actually negligible.

Option B: Recompute iterations during backward
Pros

minimizes saved state,

demonstrates checkpoint/recomputation infrastructure.

Cons

more implementation complexity,

not materially valuable for 4 × 4 matrices.

Start with Option A. Optimize only when you support much larger routing matrices.

7. Numerical requirements
This is where the feature needs more care than its code size suggests.

Positivity transform
Your POC uses:

A = exp(logits)
That is smooth and simple, but may overflow for extreme logits.

Consider supporting:

positive = exp(logits - max(logits))
or:

positive = softplus(logits) + epsilon
However, do not silently diverge from the POC during parity work. First reproduce the reference exactly; then add alternative parameterizations as explicit options.

doubly_stochastic(
    logits,
    positive="exp",
    stabilize="subtract_max"
)
Precision
Recommended policy:

parameters may be bf16/fp16,

Sinkhorn accumulation and division use fp32,

result may be cast back to model dtype,

CPU reference can use f64 for gradient checking,

cross-backend parity should compare fp32 outputs.

Convergence diagnostics
Expose:

row_error(H)
column_error(H)
stochastic_error(H)
or a general inspection result:

inspect_constraint(H, "doubly_stochastic")
Metrics:

max(abs(row_sum - 1))
max(abs(column_sum - 1))
min(H)
max(H)
spectral_norm(H)
The exact constraint is approximate after a fixed number of iterations, so the language should not describe it as mathematically exact.

9. Benchmark methodology
Your existing POC reports a strong contrast between unconstrained HC and mHC at depth, including bounded mHC gain in the tested configuration. 

For the MLPL demo, separate three claims:

Correctness
row/column sums approach one,

gradients match references,

CPU/MLX/CUDA outputs agree within tolerance.

Stability
no NaNs/Infs,

bounded gain proxy,

trainability as depth increases,

gradient norm distribution remains usable.

Performance
training steps/second,

tokens/second,

peak resident memory,

backend transfer count,

graph evaluations per step,

kernel launches if available.

Avoid combining them into a single “mHC is faster” conclusion. The paper discusses infrastructure efficiency, but a simple educational implementation may add overhead even while improving training stability.

11. MLX plan
Phase MLX-0: Literal implementation
Implement doubly_stochastic through existing MLX operations.

Goal:

parity,

not speed.

Add counters for:

Phase MLX-1: Remove eager .eval()
The current backend evaluates each primitive, preventing MLX from fusing a useful graph.

Introduce a lazy backend value:

enum TensorStorage {
    Cpu(DenseArray),
    Mlx(MlxArrayHandle),
}
Do not copy MLX results back into DenseArray after every operation.

Materialize only for:

printing,

visualization,

explicit to_device,

scalar control-flow conditions,

checkpoints,

metrics requested by the host.

Phase MLX-2: Native accelerator autograd
Your shipped MLX path currently keeps the CPU tape and rematerializes forward values on MLX. That is acceptable for parity but not for a serious mHC benchmark.

Longer term, lower a whole differentiable MLPL region to an MLX closure:

model parameters + batch -> loss
Then use MLX’s gradient transformation around that closure.

This requires a distinction between:

dynamic interpreter execution,

traceable tensor computation,

non-tensor side effects.

A scoped form could make this explicit:

compiled_graph(device="mlx") {
    loss = ...
}
Eventually train can imply this automatically.

Phase MLX-3: Composite mHC graph
Preserve:

DoublyStochastic
StreamMix
MhcLayer
through lowering so the backend can construct the whole graph before evaluation.

Phase MLX-4: Larger benchmark
Your current Tiny-LM dimensions are too small to make MLX competitive, and the documentation already records MLX running slower than CPU at that scale.

Use two benchmark classes:

Educational: runs quickly in the web/REPL.

Accelerator: d_model 256 or larger, enough batch/tokens to amortize dispatch.

12. CPU implementation plan
Initial generic implementation
Implement the operation using existing array primitives to prove semantics.

Optimized implementation
Add an internal CPU routine operating directly on contiguous memory:

pub fn sinkhorn_square(
    logits: &[f32],
    streams: usize,
    iterations: usize,
    epsilon: f32,
    output: &mut [f32],
    scratch: &mut [f32],
)
For stream mixing, avoid materializing transposed tensors:

pub fn mix_stream_axis(
    matrix: &[f32],
    input: &[f32],
    outer: usize,
    streams: usize,
    features: usize,
    output: &mut [f32],
)
Where:

outer = batch × tokens
This can become a simple cache-friendly loop.

CPU advantages
no kernel launch overhead,

excellent for S=4,

easy to inspect,

transformer matmuls dominate at useful dimensions,

interpreter dispatch can obscure the low cost of mHC itself.

The compiled CPU path should therefore be included in benchmarks separately from the interpreter.

Bottom line
Adding meaningful mHC support is very feasible. The CPU reference and language-level implementation are relatively straightforward because your existing MLPL operation set is already sufficient. The feature also fits naturally with MLPL’s strongest differentiators: named axes, inspectable models, portable source, built-in visualization, and backend parity.

The larger project is not mHC itself. It is evolving sw-MLPL from per-operation accelerator dispatch toward graph-level accelerator lowering. mHC is an excellent driver for that work because it:

contains a recognizable composite mathematical operation,

stresses autograd and lazy fusion,

has tiny inspectable matrices,

has existing MLX and CUDA/PyTorch reference implementations,

and offers a clear cross-backend stability demonstration.

I would make the first deliverable a CPU/WASM Sinkhorn and stream-mixing tutorial, then a generic mhc_block, then reproduce the existing depth sweep. MLX correctness should follow immediately, while MLX performance and CUDA become separate backend engineering milestones rather than blockers for shipping the language feature.
