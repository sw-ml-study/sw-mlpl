Conclusion
Yes, you can retrofit Engram-style conditional memory into Gemma, Qwen, Llama, Ornith, and most decoder-only Transformer models in the 12B–70B range. However, it is not a transparent inference cache like a KV cache. You must:

Insert one or more Engram modules into the model.

Train the memory tables, projections, and gates against the frozen—or partly frozen—base model.

Extend the inference runtime so it executes the lookup and fusion operations.

Use the same tokenizer normalization, hashing, layer placement, and table geometry at training and inference.

The most practical target for your hardware is:

A frozen, quantized 12B–32B base model plus two low-dimensional Engram modules, trained with QLoRA/PEFT and deployed through MLX on Apple or PyTorch/CUDA on NVIDIA.

I would not begin by wrapping every layer or storing full-width hidden vectors. Your current POC does both, and that becomes expensive very quickly.

1. What your current POC proves—and what should change
Your repository has evolved through two related but materially different ideas.

Behavioral approximation
The initial LoRA experiments taught a model to behave as though it had deterministic lookup. Your Part 2 post describes this as pattern injection plus LoRA, rather than an actual architectural lookup table. 

That approach is useful for:

Testing datasets and pattern categories.

Learning whether predictable local mappings are useful.

Comparing MLX and CUDA training workflows.

Establishing evaluation tasks.

It does not avoid neural computation during inference because the Transformer still generates the result conventionally.

Actual hash-based memory
Your current EnhancedEngramModule performs a real embedding-table lookup and gated residual injection. It hashes token IDs, gathers multiple embedding rows, averages or attends over them, gates the result, and projects it into the residual stream.

The wrapper already recognizes Llama, Qwen2, Gemma, Mistral, Phi and several related Hugging Face layouts.

That means you have much of the mechanical model-wrapping infrastructure, but the current module differs from DeepSeek’s design in important ways.

Current POC limitations
Your current hashing is essentially:

hash(token_id) = token_id × prime mod table_size
This hashes individual tokens, not contextual N-grams.

More significantly, the table stores d_model values:

memory_table[table_size, d_model]
and your wrapper creates a separate table for every injected layer.

For a model with hidden size 5,120:

100,000 entries × 5,120 dimensions × 2 bytes
≈ 0.95 GiB per Engram layer
Injecting this into 40 layers would require roughly 38 GiB just for memory tables, before the base model, KV cache, temporary activations, projections, or optimizer state.

The README currently says the wrapper can inject every Transformer layer, but that is only reasonable for small demonstration models.

2. Use a closer-to-paper architecture
The official demonstration is much more memory-efficient than your current POC.

It uses:

Normalized/compressed token IDs.

Bigram and trigram keys.

Multiple independent hash heads.

Low-dimensional memory values.

Concatenation of the retrieved head vectors.

Projection into the model hidden dimension.

Context-aware gating using the current hidden state.

Engram injection into only selected layers.

The official code retrieves 2-gram and 3-gram embeddings, flattens the multi-head results, projects them to hidden width, computes a hidden-state-dependent gate, and adds a short convolutional transformation.

Recommended portable Engram block
For Gemma/Qwen/Llama/Ornith, I recommend this simplified first production architecture:

token IDs
   │
   ├── normalization/compression
   │
   ├── rolling bigram/trigram hashes
   │
   ├── H independent embedding lookups
   │
   └── concatenate or weighted sum
                │
             RMSNorm
                │
        low-rank value projection
                │
 hidden state ──┼── context gate
                │
       gated residual addition
Use:

2 injected layers
2 N-gram orders: 2 and 3
4 hash heads per N-gram initially
32–64 dimensions per head
one table region per N-gram/head
one projected value per token
Skip the short convolution in the first implementation. It adds architectural fidelity, but not enough value to justify complicating the first MLX and CUDA ports.

3. Memory budgeting
The important formula is:

table bytes =
  injected_layers
× ngram_orders
× hash_heads
× slots_per_head
× dimensions_per_head
× bytes_per_value
Projection and gate parameters are relatively small compared with the tables.

Example A: Conservative 18GB Apple configuration
Injected layers:       2
N-gram orders:         2
Heads per N-gram:      4
Slots per head:        262,144
Dimensions per head:   32
Table type:            FP16
Memory:

2 × 2 × 4 × 262,144 × 32 × 2
= 536,870,912 bytes
≈ 512 MiB
This is a realistic Engram addition to a 12B model stored at 4-bit.

Example B: Strong 24GB NVIDIA configuration
Injected layers:       2
N-gram orders:         2
Heads per N-gram:      8
Slots per head:        524,288
Dimensions per head:   32
Table type:            BF16
Memory:

2 × 2 × 8 × 524,288 × 32 × 2
≈ 2 GiB
This is large enough to test meaningful capacity while still leaving room for a quantized 12B–20B backbone and a useful KV cache.

Example C: 64GB Apple configuration
Injected layers:       2
N-gram orders:         2
Heads per N-gram:      8
Slots per head:        1,048,576
Dimensions per head:   64
Table type:            FP16
Memory:

2 × 2 × 8 × 1,048,576 × 64 × 2
≈ 8 GiB
This is approaching the official design’s large-memory character, but it would be a poor first experiment. Start around 1–2 GiB and scale only after controlled ablations.

Official demo scale
The official demo defaults to two N-gram orders, eight heads per order, approximately five times tokenizer vocabulary entries per head, and 64 dimensions per head.

With a roughly 129K-token vocabulary, that works out to approximately:

2 N-gram orders
× 8 heads
× ~646K slots
× 64 dimensions
≈ 661 million memory parameters per injected layer
At FP16, that is around 1.23 GiB per layer, or roughly 2.5 GiB for two layers, excluding projections. This is feasible next to a 4-bit 12B–20B model on a 24GB GPU, but tight once training activations and optimizer state are included.

Vectorized rolling hash
Do not use Python loops per token. Construct shifted arrays:

current = ids
previous_1 = pad_left(ids, 1)
previous_2 = pad_left(ids, 2)
Then compute:

bigram_mix  = current*M0 XOR previous_1*M1
trigram_mix = current*M0 XOR previous_1*M1 XOR previous_2*M2
Each head applies a different modulus and/or mixing seed.

The official implementation uses shifted token arrays, per-position multipliers, XOR mixing and different prime-sized tables.

Table layout
Use one contiguous array rather than many small embedding objects:

[all bigram-head tables][all trigram-head tables]
Precompute offsets:

global_index = table_offset[ngram, head] + local_hash
Then perform one flattened gather.

That layout maps well to:

mx.take

PyTorch embedding

CUDA gather kernels

llama.cpp/GGML tensor storage later

Layer integration
Modify the architecture-specific decoder block rather than wrapping arbitrary __call__ methods.

Conceptually:

residual = hidden
hidden = attention(norm(hidden), cache)
hidden = residual + hidden

if layer_index in engram_layers:
    hidden = hidden + engram(hidden, token_ids)

residual = hidden
hidden = mlp(norm(hidden))
hidden = residual + hidden

At the start of selected blocks, matching the official high-level ordering.

Do not inject after the entire original block as your current wrapper does. Your wrapper currently calls the complete original layer and then appends Engram to its output. That is convenient, but it does not reproduce the same interaction with attention and MLP.

5. NVIDIA implementation
First implementation: PyTorch
Begin with a clean PyTorch implementation using:

torch.nn.Embedding

CUDA-resident hash indices

BF16 tables

Hugging Face model subclasses

PEFT/LoRA or Unsloth only where it does not rewrite the relevant blocks

torch.compile after correctness is established

Do not convert input IDs to NumPy, as the official demonstration does for clarity. The official code constructs hashes on the CPU and turns them back into a Torch tensor. That would force synchronization and transfers during every forward pass.

All normalization and hashing should remain on CUDA:

compressed = compression_lut[input_ids]
hashes = cuda_ngram_hash(compressed)
memory = F.embedding(global_indices, memory_table)
Training configuration for 24GB
For a 12B–14B model:

Base weights:         4-bit
Base parameters:      frozen
Engram table:         BF16 or FP16
Engram table size:    0.5–2.0 GiB
Gate/projections:     BF16
Optimizer:            8-bit AdamW or Adafactor
Sequence length:      2K initially
Microbatch:           1
Gradient checkpoint:  enabled where useful
The difficult part is not inference capacity. It is optimizer and gradient memory.

A 2 GiB BF16 table generally entails approximately:

2 GiB parameters
+ 2 GiB gradients
+ optimizer states
With ordinary FP32 Adam moments, optimizer state alone can add roughly 8 GiB. Therefore:

Use an 8-bit optimizer.

Train only a subset of table rows when possible.

Consider row-sparse updates.

Or begin with a 256–512 MiB memory table.

Sparse update issue
nn.Embedding(..., sparse=True) can produce sparse gradients, but the rest of the training stack, optimizer, compilation path and distributed framework must all support them correctly. A practical progression is:

Dense gradients with a small table.

Row-sparse optimizer for the table.

Separate optimizer groups for tables versus gates/projections.

Custom fused lookup/backward only after profiling.

Triton or custom CUDA kernel
Initially, hashing and embedding gather can remain separate Torch operations.

A fused kernel becomes valuable when profiling shows overhead from:

Creating shifted N-gram tensors.

Repeated modular arithmetic.

Constructing head offsets.

Materializing [batch, sequence, ngram, head] indices.

Multiple embedding gathers.

A fused CUDA/Triton kernel can:

Read current and previous compressed token IDs.

Calculate all hashes.

Add table-region offsets.

Gather low-dimensional values.

Concatenate or sum the heads.

Do not fuse the gate and value projection initially; GEMM libraries already execute those operations efficiently.

7. Can this be added without retraining the whole model?
Yes, but not without any training.

Use a staged procedure.

Stage 1: Frozen base, train Engram only
Train:

Memory table.

Value projection.

Gate/key projection.

Optional memory normalization.

Freeze:

Token embeddings.

Attention.

MLP.

Output head.

All base model norms.

Initialize the output path near zero so the modified model initially reproduces the base model. Your current module already attempts this by biasing the gate toward zero and initializing the merge projection with small values.

This is the safest first stage.

Stage 2: Engram plus nearby LoRA
Add LoRA to:

Attention output projection in the injected layers.

MLP down projection in the injected layers.

Possibly adjacent layer norms or a small adapter.

This allows the base network to learn to consume the memory without changing billions of weights.

Stage 3: Partial continued pretraining
Unfreeze:

The injected blocks.

One block before and after each Engram block.

Engram components.

This is more likely to produce the paper’s claimed effect of freeing early-layer capacity, because the surrounding layers can reorganize their responsibilities.

Stage 4: Full pretraining-style experiment
This is needed for a scientifically strong claim that an Engram-enhanced architecture outperforms an iso-parameter baseline. The DeepSeek work trained Engram as part of the architecture and reports gains across knowledge, reasoning, code, math and long-context retrieval. 

A retrofit trained on a modest corpus is more properly described as:

Engram-augmented continued pretraining or PEFT, not a reproduction of the complete Engram scaling result.

9. Collision handling
Do not assume collision-free lookup is automatically superior.

The Engram-Nine study found that a collision-free high-frequency tier did not consistently improve validation loss and suggested that collisions may act as regularization; it also identified gate credit assignment as a possible larger problem than hash precision. 

Therefore, evaluate at least:

Single hash.

Four independent heads.

Eight independent heads.

Exact hot tier plus hashed cold tier.

Shared table versus separate per-N-gram tables.

Mean, concatenate/project and learned head weighting.

The most important diagnostic is not merely collision count. It is:

loss by key frequency
gate value by key frequency
loss by collision count
gate value by collision count
Your conditional wrapper’s regex-based route confidence is useful for demos, but it is separate from the model’s learned, token-level context gate. The paper-style gate should decide independently at every token position.

10. Host-memory offload
Apple Silicon
There is no discrete host/device boundary in the NVIDIA sense, but bandwidth and residency still matter. A large randomly accessed table competes with base weights and KV cache for unified-memory bandwidth.

Keep the first table fully resident and measure:

Gather bandwidth.

Page faults.

Wired memory.

Decode latency.

Prompt-processing latency.

Because decode performs very few token lookups at each step, table capacity can be relatively large. Prompt processing creates many simultaneous random accesses and is more likely to expose bandwidth issues.

NVIDIA
The Engram paper specifically argues that deterministic addressing allows host-memory prefetch and low-overhead offload. 

A realistic tiered design is:

GPU hot table
    Frequent N-grams, low latency

Pinned CPU warm table
    Less frequent rows, asynchronously prefetched

Optional mapped/cold store
    Large experimental memory, slower path
However, PCIe random row fetches can easily dominate decode latency. Batch and prefetch all required rows for:

The entire prompt during prefill.

The next token position during decoding.

All injected layers together when the addressing scheme permits it.

The CXL Engram work reinforces that sparse, predictable accesses are amenable to lower-tier memory, but its near-DRAM results depend on specialized CXL infrastructure and SGLang integration, not ordinary PCIe paging. 

For your 24GB systems, keep the first implementation entirely in VRAM.

A compact first surface could be:

        ngrams = [2, 3],
        heads = 4,
        slots = 65536,
        head_dim = 16,
        seed = 42
    )
)
You need the input token IDs as well as the hidden-state tensor, so Engram is not quite an ordinary unary layer. There are three reasonable interfaces.

Option A: Explicit two-input operation
h = apply_engram(memory, h, token_ids)
Pros

Semantics are obvious.

Easy to test.

No hidden execution context.

Useful for instructional demos.

Cons

Less elegant inside chain.

Transformer builders must special-case the layer.

Option B: Context-aware model layer
h = apply(memory, h)
The evaluator carries token IDs in a model execution context.

Pros

Composes naturally with existing Model DSL layers.

Similar to attention accessing masks or caches.

Better eventual model-import surface.

Cons

More evaluator machinery.

Hidden dependencies can complicate debugging.

Option C: Structured Transformer state
state = {
    hidden: h,
    tokens: token_ids,
    position: positions,
    mask: mask
}

state = apply(memory, state)
Pros

Architecturally clean.

Scales to KV caches, masks, rotary positions, MoE routing, and recurrent state.

Avoids continually adding special arguments.

Cons

A larger language/runtime change.

Likely beyond the first Engram demo.

Recommendation
Start with Option A, but define the internal trait so it can later accept a structured execution context:

pub struct LayerContext<'a, T> {
    pub token_ids: Option<&'a T>,
    pub positions: Option<&'a T>,
    pub attention_mask: Option<&'a T>,
    pub training: bool,
}
The MLPL syntax remains explicit initially:

h = apply_engram(e, h, ids)
3. Define a backend-neutral Engram specification
The most important new type should contain no MLX, CUDA, Candle, or CPU tensor types.

#[derive(Debug, Clone, PartialEq, Eq)]
pub struct EngramSpec {
    pub hidden_size: usize,
    pub ngram_orders: Vec<usize>,
    pub heads_per_ngram: usize,
    pub slots_per_head: usize,
    pub head_dim: usize,
    pub seed: u64,
    pub use_short_conv: bool,
    pub kernel_size: usize,
}
Validation should reject:

Empty N-gram lists

N-grams below 2

Zero heads

Zero slots

Zero dimensions

Overflow in total parameter calculation

Unsupported convolution combinations

Hidden-size/projection mismatches

Add derived methods:

impl EngramSpec {
    pub fn table_rows(&self) -> Result<usize, EngramError>;
    pub fn retrieved_width(&self) -> Result<usize, EngramError>;
    pub fn parameter_count(&self) -> Result<u64, EngramError>;
    pub fn bytes_for(&self, dtype: DType) -> Result<u64, EngramError>;

That lets the REPL provide useful introspection:

mlpl> :describe e

This is especially important before moving to 12B-plus models, where an accidental full-hidden-width table can consume tens of gigabytes.

4. Engram operations required by the language
You do not need a large new tensor-operation surface.

The minimal Engram implementation requires:

token normalization LUT lookup
left shift/pad
integer multiply
bitwise XOR
integer modulo
embedding gather
reshape/flatten
linear projection
RMSNorm
elementwise multiply
sum-reduce
signed square-root transform
sigmoid
residual addition
Optional later operation:

depthwise causal conv1d
sw-MLPL already has embedding layers, linear layers, RMS normalization, residual composition, autograd, and optimizers.

The likely missing primitives are:

Integer bitwise XOR

Integer modulo on device tensors

Efficient multi-index gather

Shift-and-pad

Possibly grouped/depthwise 1D convolution

These are useful general MLPL operations beyond Engram, so expose them at the array/runtime layer rather than hiding them in one model implementation.

5. Do not hash on the CPU for the accelerated path
The reference DeepSeek demonstration creates N-gram hashes using NumPy and converts them into a Torch tensor afterward. That is appropriate for explanatory code but wrong for an MLPL accelerator implementation. The reference computes shifted N-grams with arrays, XORs multiplier products, applies per-head modulus, and stacks the results.

For MLPL, both CPU and GPU should implement the same operation:

fn ngram_hashes(
    token_ids: &Tensor,
    spec: &HashSpec,
) -> Result<Tensor, BackendError>;
Input:

[B, T]
Output:

[B, T, N, H]
where:

N is the number of N-gram orders.

H is the number of heads per order.

The intermediate implementation can use ordinary MLX operations:

shift
multiply
xor
remainder
stack
Later, replace that group with one fused Metal kernel.

6. Table layout
Do not model each head as an independent high-level object.

Use one contiguous memory parameter:

memory_table:
    [total_rows, head_dim]
and a static offset tensor:

head_offsets:
    [ngram_count, heads_per_ngram]
Then:

local_hashes = hash(...)
global_indices = local_hashes + head_offsets
retrieved = gather(memory_table, global_indices)
Result:

[B, T, N, H, head_dim]
Then flatten:

[B, T, N * H * head_dim]
The DeepSeek demo uses the same general offset strategy: separate logical tables are represented as a single embedding table plus per-head offsets.

This representation has several advantages:

One serialized tensor

One gather operation

Simple safetensors naming

Easy device transfer

Easier table quantization

Easier Metal/CUDA kernel fusion

Fewer tiny parameter objects in the MLPL model tree

7. Rust-side model representation
Extend the model layer enum with a compact Engram variant:

pub enum Layer {
    Linear(LinearLayer),
    Embed(EmbedLayer),
    RmsNorm(RmsNormLayer),
    Attention(AttentionLayer),
    Residual(Box<Layer>),
    Chain(Vec<Layer>),
    Engram(EngramLayer),
}
Where:

pub struct EngramLayer {
    pub spec: EngramSpec,
    pub params: EngramParams,
}
And:

pub struct EngramParams {
    pub memory: ParameterId,
    pub value_weight: ParameterId,
    pub value_bias: Option<ParameterId>,
    pub key_weight: ParameterId,
    pub gate_norm: ParameterId,
    pub query_norm: ParameterId,
}
For the first version, simplify the gate.

First gate
retrieved = project(memory_vectors)
gate = sigmoid(linear(concat(hidden, retrieved)))
output = hidden + gate * retrieved
This resembles your existing POC and is easier to express using the current MLPL operation set.

Paper-style gate later
key   = RMSNorm(key_projection(memory))
query = RMSNorm(hidden)
score = reduce_sum(key * query) / sqrt(hidden_size)
score = signed_sqrt(score)
gate  = sigmoid(score)
value = gate * value_projection(memory)
output = hidden + value
The demonstration implementation computes this hidden-state-conditioned gate and then applies a short convolution to the value path.

I would ship both as explicit modes:

engram(..., gate = "concat")
engram(..., gate = "dot")
The "concat" gate is the pedagogical implementation. The "dot" gate is the closer paper reproduction.

8. MLX implementation strategy
Your present MLX backend is correct but has a major performance problem: each operation copies f64 -> f32, evaluates immediately, and copies results back to CPU.

That architecture cannot support useful 12B model inference.

Engram therefore creates a forcing function for an MLX runtime redesign.

Current model
DenseArray
  -> create MLX array
  -> execute one op
  -> eval()
  -> copy into DenseArray
  -> repeat
Required model
MLPL TensorHandle
  ├── CPU(DenseArray)
  └── MLX(MlxArrayHandle)
Operations inside:

device("mlx") {
    ...
}
must remain as MLX arrays until:

to_device(x, "cpu")
or formatting requires materialization.

Your architecture already says device-scoped tensors should stay on-device until an explicit transfer. Engram should be built only after this becomes true in-process, even if the backend-as-service refactor comes later.

MLX Engram execution
A Rust trait might be:

pub trait EngramBackend {
    type Tensor;

    fn ngram_hash(
        &self,
        ids: &Self::Tensor,
        spec: &HashSpec,
    ) -> Result<Self::Tensor>;

    fn gather_rows(
        &self,
        table: &Self::Tensor,
        indices: &Self::Tensor,
    ) -> Result<Self::Tensor>;

    fn apply_engram(
        &self,
        layer: &EngramDeviceParams<Self::Tensor>,
        hidden: &Self::Tensor,
        ids: &Self::Tensor,
    ) -> Result<Self::Tensor>;
}
The MLX backend implementation should:

Keep IDs as integer MLX arrays.

Build shifted views or arrays.

Compute hashes lazily.

Perform one flattened gather.

Project and gate.

Return an unevaluated MLX array.

Evaluate only at a model boundary or explicit synchronization point.

sw-MLPL already uses mlx-rs as its optional Rust binding.

10. CUDA choices later
There are three main Rust-only approaches.

A. Candle CUDA backend
Best first CUDA implementation.

Advantages:

Tensor abstraction already exists.

CUDA kernels are included.

Transformer models and safetensors loading already exist.

Custom operations can be added.

CPU/CUDA behavior can be parity tested. 

Disadvantages:

MLPL must adapt its runtime to Candle tensor semantics.

The MLX and CUDA implementations would use different lower-level libraries.

Some duplication of backend glue.

Possible design:

mlpl-cuda
  -> Candle Tensor
  -> Candle CUDA Device
  -> custom Engram hash/gather op when needed
B. cudarc
Best for direct control.

Advantages:

Rust-level CUDA driver and library access.

Direct allocation, streams, kernels, cuBLAS, and related APIs.

Suitable for a purpose-built Engram kernel.

Disadvantages:

You must build much more of the tensor runtime.

Autograd, broadcasting, indexing, model loading, and shape handling become your responsibility.

Better as a lower layer than as the initial complete backend.

cudarc remains active and exposes low-level CUDA capabilities, but active feature requests around memory pools, stream capture, pinned allocations, and newer CUDA APIs illustrate that it is a low-level foundation rather than a full ML framework. 

C. Burn
Potentially useful if MLPL wants one Rust abstraction with multiple backends, but it would compete with sw-MLPL’s own backend-neutral abstraction.

Recommendation
Use:

Apple: mlx-rs
NVIDIA phase 1: Candle CUDA
NVIDIA phase 2: custom cudarc kernel behind mlpl-cuda
Keep both behind the same EngramBackend contract.

13. Parameter freezing and sparse memory training
Your current MLPL optimizer model appears oriented toward dense parameter trees. Engram tables will expose a scaling problem.

A table such as:

262,144 slots
× 4 heads
× 2 N-grams
× 32 dimensions
contains approximately 67 million values per injected layer.

Dense Adam state can dominate memory.

You need at least:

pub enum ParameterUpdate {
    Dense,
    IndexedRows,
    Frozen,
}
For Engram memory:

IndexedRows
The backward pass should return:

IndexedGradient {
    rows: Tensor,
    values: Tensor,
}
rather than allocating a gradient tensor with the full table shape.

This enables:

Sparse SGD

Sparse Adam

Lower unified-memory use

Larger tables

Faster training

Realistic 18GB operation

Implement dense gradients for the tiny demo, but make sparse indexed gradients an explicit milestone before attempting 12B fine-tuning.

16. Architectural decision: service versus in-process
Your current project architecture says the canonical future design should make device backends services rather than linked features, partly because one orchestrator should not have to link both MLX and CUDA.

That remains sensible, but Engram should not wait for it.

Use three layers:

mlpl-engram-core
    Specs, hashes, metadata, backend contracts

mlpl-mlx
    In-process MLX implementation

mlpl-mlx-serve
    Thin RPC wrapper around mlpl-mlx
Later:

mlpl-cuda
mlpl-cuda-serve
The service API should operate at a coarse grain:

load model
create Engram
run training step
generate
inspect statistics
save checkpoint
Do not RPC individual gather or matmul operations.

18. Immediate technical priority
The highest-priority work is not importing Gemma or Qwen.

It is:

Change sw-MLPL’s tensor representation so an MLX value remains an MLX value across an entire expression or model forward pass.

The current backend intentionally re-materializes each operation and sends values back through CPU-resident DenseArray storage. That design is adequate for functional parity but incompatible with:

Multi-billion-parameter models

Large embedding tables

Engram random gathers

Quantized inference

Efficient autograd

Meaningful MLX graph fusion

Once persistent device tensors exist, Engram itself is relatively modest: hashing, gather, projection, gate, and residual addition.

Recommended end-state
                           sw-MLPL source
                                  |
                           typed Model DSL
                                  |
                    backend-neutral model graph
                       /          |          \
                    CPU          MLX         CUDA
                 reference     mlx-rs       Candle
                                               |
                                      optional cudarc kernels
Engram becomes one graph node with a standard contract rather than a special external subsystem:

EngramNode {
    hidden,
    token_ids,
    memory_table,
    hash_spec,
    gate_params,
    projection_params
}
That gives you exactly the demonstration your language is meant to support:

device("mlx") {
    model = transformer(..., engram = ...)
    train ...
    generate ...
}
The same .mlpl source can later run under:

device("cuda") { ... }
without Python and without changing the Engram model definition.
