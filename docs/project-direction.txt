Revised understanding of sw-MLPL
The earlier roadmap understated the project’s current maturity.

The most important corrections are:

Engram is no longer merely planned. E1 primitives, E2 DSL/training support, and E3 Tiny-LM integration are complete. The implementation includes deterministic n-gram addressing, trainable memory, tape differentiation, in-chain insertion after attention, frozen-base training, collision statistics, gate statistics, and end-to-end demos.

MLX is not just an external service or CPU-backed experiment anymore. Metal has been enabled, a backend-neutral TensorHandle abstraction exists, lazy MLX tensors remain resident through the forward tape, and gradients now remain resident during backward for the principal operation set.

The active AgentRail saga is E4, currently at step 6, not an early MLX implementation milestone. The next work is optimizer residency, parity, benchmarking, and cleanup—not creating an MLX backend from scratch.

sw-MLPL already has substantial notebook/research infrastructure: datasets, tokenization, experiment tracking, autograd, optimizers, training blocks, model DSL, compilation to Rust, visualization, server sessions, SSE training telemetry, cancellation, remote MLX execution, LoRA, feasibility estimation, and LLM calls. The older docs/status.md captures many of these completed sagas, although its “next saga” section has clearly fallen behind the active E-series work.

CUDA is also not completely greenfield. CUDA/Candle crates exist and are target-gated; the outstanding work is Linux validation, resident tensor integration, backend completeness, and performance—not simply introducing a CUDA feature flag.

The current E4 plan confirms that the key architectural change is a device-aware autograd tape and resident optimizer state, with MLX performance—not mere functional parity—as the acceptance criterion.

I could not retrieve the body of the separate GitHub wiki repository through the available GitHub connector, and the public raw/wiki fetch was unavailable. I therefore have not treated individual errata entries as authoritative. The main repository itself explicitly says the errata page contains stale and already-resolved claims and schedules a separate audit against current code and commit history.

Revised strategic focus
Your four priorities remain the correct organizing principle, but they should now be mapped onto the existing architecture:

Program	What sw-MLPL already has	What should be added
Generation speed	Tiny LM, sampling, MLX, resident tape underway	KV cache, MTP, speculative verification, generation benchmarks
Agent quality	llm_call, server sessions, experiments, LoRA	trajectory model, ICL retrieval, ICRL, evaluators, replay
Colab replacement	DSL, autograd, training, datasets, visualization, web REPL	import/export, sweeps, checkpointing, richer metrics, reproducible reports
Small/old hardware	CPU reference, compile-to-Rust, CUDA crates, feasibility estimates	quantized inference, recursive models, SIMD kernels, sparse/int operations
The revised roadmap should therefore finish the execution substrate first, then build MTP and feedback research on top of it.

Recommended milestone ordering
Milestone 1 — Finish E4 resident training
This is the immediate priority because almost every speed-related feature depends on it.

The active plan’s remaining functional work should be completed before introducing a separate MTP saga:

Resident Adam and momentum state.

Persistent parameters across training steps.

Explicit synchronization only at observable boundaries.

Tiny-LM CPU/MLX trajectory parity.

End-to-end benchmarks proving MLX is faster than the CPU interpreter.

Identification of every silent CPU fallback.

Cleanup of superseded MLX fast paths.

The original E4 acceptance criterion is specifically:

Tiny-LM training on MLX must become faster than CPU.

That is much better than the generic “GPU support” milestone I previously suggested.

Add one change to E4
Instrument synchronization and fallback events now:

device_uploads
device_downloads
implicit_syncs
cpu_fallback_ops
resident_tensor_peak
graph_forces
kernel_submissions
This instrumentation will later explain why an MTP or speculative implementation is—or is not—faster.

Exit criteria
Optimizer state remains on MLX across steps.

No complete model re-upload per iteration.

One scalar loss download per reporting interval, rather than arbitrary tensor materialization.

Tiny-LM training ratio exceeds 1.0× versus the interpreted CPU path.

Benchmark output identifies fallback and synchronization counts.

Milestone 3 — Generation runtime foundation
My previous roadmap jumped too quickly from ordinary Tiny-LM sampling to MTP. The repository first needs a reusable incremental-generation engine.

3.1 Generation state
Introduce an explicit generation-session object:

struct GenerationState {
    token_ids: TensorHandle,
    position: usize,
    model_state: ModelState,
    kv_cache: Option<KvCache>,
    rng_state: RngState,
}
At the MLPL level:

g = begin_generate(model, prompt)
g, logits = generation_step(g)
g, tokens = generation_steps(g, 16)
3.2 KV cache
The existing Tiny-LM generation path should gain:

per-layer K/V state

append without recomputing the prefix

cache reset and clone

cache memory accounting

CPU and MLX implementations

cache-equivalence tests against full-prefix recomputation

3.3 Batched verification
Add a primitive that can score multiple proposed future tokens in one target invocation:

scores = verify_sequence(target, state, proposed_tokens)
This becomes the common substrate for:

self-speculative MTP

draft-model speculation

tree proposals

recursive lookahead

3.4 Correct sampling semantics
Separate:

greedy acceptance

exact speculative sampling

approximate research modes

A demo must identify which semantics it uses rather than reporting one undifferentiated speed number.

Exit criteria
Cached generation is measurably faster than full-prefix generation.

Cached and uncached greedy output are identical.

Sampling distributions pass statistical comparison tests.

Target verification can process a proposed token block without N independent full forward calls.

Milestone 4 — Multi-token prediction
MTP should now become the highest-priority new ML feature.

4.1 Training-time MTP
Add a model-layer abstraction rather than a one-off Tiny-LM implementation:

    horizons=[1, 2, 3, 4]

    heads,
    hidden,
    targets,
    weights=[1.0, 0.5, 0.25, 0.125]
)
Capabilities required:

4.2 MTP experiments
Compare at least:

Partial trunk unfreezing.

This matters because “add four output heads” and “obtain useful speculative proposals” are not equivalent.

4.3 Self-speculative decoding
Use the generation runtime from Milestone 3:

    ↓
MTP heads propose k tokens
    ↓
target verifies proposed block
    ↓
accept valid prefix
    ↓
repair first rejected token
Track:

4.4 Adaptive proposal length
Do not always generate all heads.

Use head confidence or learned acceptance prediction:

k = choose_mtp_depth(head_distributions, threshold=0.82)
This may matter considerably on older hardware, where the extra head computation can cost more than it saves.

4.5 MTP introspection
This aligns with your interest in observable learning:

show confidence

plot acceptance by token type

visualize whether farther heads learn syntax, punctuation, identifiers, or repeated phrases

Featured demos

MTP CPU vs MLX: determine where proposal overhead becomes worthwhile.

Exit criteria
Genuine wall-clock improvement over cached autoregressive decoding.

Quality-equivalent generation under an exact verifier.

At least one model small enough to run comfortably on CPU.

Acceptance and cost are fully observable.

Where mHC belongs
The queued plan sensibly divides mHC into:

reusable constrained tensor transforms

a multi-stream residual ModelSpec

CPU implementation

MLX residency

CUDA parity later

That is the right technical decomposition.

In your four-priority roadmap, however, mHC should probably sit after E5 and before or alongside the generation-runtime work, not ahead of MTP.

Reasons to proceed soon:

it validates the expanded model DSL

it exercises resident tensor transforms

it provides quality/stability experiments

the CPU and MLX primitives mostly exist

Reasons not to let it dominate:

it does not directly provide an inference speedup

it does not establish the generation state needed by MTP

it does not create the agent feedback substrate

its multi-stream representation may initially increase compute and memory

I would implement mHC as a bounded three-saga track:

mHC-P1 constrained transforms
mHC-P2 CPU model layer + stability demo
mHC-P3 resident MLX parity/performance
Then return immediately to KV-cache and MTP.
