# Loose Coupling: techniques for compact, readable code

This is the canonical reference for HOW to write code that
fits the project's [code metrics](code_metrics.md) gates
without playing tricks. The metrics (25 LOC per function,
7 functions per module, 7 modules per crate, 500 lines per
file) assume idiomatic formatting. When a function or
module is over budget, the answer is **never** to compress
whitespace or fight `rustfmt`. The answer is to restructure
the code so that each piece does one thing and the pieces
compose cleanly.

Three complementary lenses drive every refactor:

1. **Phase separation.** Code runs at one of four phases
   (compile time, start-up, conditional, dataflow). Identify
   which phase each piece belongs to and move it there.
2. **Compose, don't compress.** A function is wide when it
   is doing two or three things. Split by responsibility,
   then compose the small pieces with delegation, iterator
   pipelines, or monadic chains. Functional style is the
   compact style.
3. **Define once, invoke many.** When a pattern repeats
   across N call sites, define it ONCE (as a macro, a
   helper function, a trait method, a const table) and
   spend one line per use site. Definition lives in one
   module; uses are line-cheap everywhere.

The rest of this document expands each lens into concrete
patterns and anti-patterns. The patterns are not optional --
they are the rules the metrics budget assumes.

A symptom -> technique table at the end maps common
sw-checklist issues to the specific pattern that retires
them.

## Phase 1: compile time

What can be computed when `cargo build` runs has zero
runtime cost. Anything constant -- lookup tables, default
configs, parser keyword sets, builtin dispatch tables --
belongs here.

**Patterns:**

- `const` items for primitive constants and `&[T]` slices of
  `Copy` data.
- `static` items for non-Copy data (e.g. owned `String`s, but
  prefer `&'static str` where possible).
- `const fn` helpers so derived constants stay
  compile-time-evaluable.
- `macro_rules!` and proc macros to generate repetitive
  boilerplate (impl blocks, builtin registrations).
- Generic functions with monomorphization: the same source
  specializes per concrete type, no runtime dispatch.
- Type-state encodings: encode invariants in the type system
  so the compiler enforces them at zero runtime cost.

**Example in this repo.** `mlpl-eval-core::inspect_groups`
exposes `BUILTIN_GROUPS: &[FnGroup]` as a `const`. The
inspection module just iterates over it -- the table itself
is compiled into the binary, no allocation, no setup.

**Anti-pattern:** building a lookup table inside the
function that uses it. Hoist to `const`.

### Macros: define once, invoke many times (compile time)

Macros are the project's most powerful "define once,
invoke many" tool, and they cost almost nothing at the
invocation site:

- **The macro definition is one place**, counted against
  whatever module owns it.
- **Each macro invocation is one line** of source at the
  call site. The expanded code is generated by the
  compiler and never appears in your `.rs` files; only the
  invocation does. The expansion's LOC does not count
  against the surrounding function's budget. (Generated
  code does compile, of course; the budget that cares is
  source lines per source function.)

This is **the right answer** when the same shape repeats
five or more times. Examples in this repo:

- `mlpl-runtime::builtins`'s `check_arity!($name, $expected, $args)`
  macro replaces 6+ lines of `if args.len() != N { return
  Err(RuntimeError::ArityMismatch { ... }) }` boilerplate
  with one line per builtin. ~25 invocations across the
  runtime; without the macro, each builtin function would
  blow its 25-LOC budget on argument-count checks.

- `mlpl-runtime-core::Xorshift64`'s pattern of "next_u64
  / next_f64 / next_normal" could be replaced with a
  `define_next_n!(u64, f64, normal)` macro if it grew (it
  doesn't need to today, but the option is in the toolbox).

**Patterns:**

- `macro_rules!` for declarative pattern-matching macros.
  Place definitions near the family of functions they
  serve; export via `#[macro_export]` only if cross-crate
  consumers need them.
- Proc macros for derive-style generation
  (`#[derive(...)]`) or attribute-driven generation
  (`#[my_macro]`). More setup cost; appropriate when the
  generated code follows a complex schema (custom derive
  for a trait, route registration, etc.).
- `paste!` for token concatenation when you want to
  generate `get_foo` and `set_foo` from a `foo` input.
- `Builder`-style macros for repetitive struct field
  declarations + accessors.

**When to reach for a macro:**

- The same `if ... { return Err(...) }` shape repeats >=
  5 times in one module. Macro it.
- A registry of N items each needs `name`, `signature`,
  `docs`, and `dispatch_arm`. Define a single
  `register_builtin!(name, sig, doc, body)` macro and
  invoke once per builtin.
- Boilerplate over an enum variant set: a single macro
  that takes the variant name and generates the
  matching `From`, `Display`, and arm patterns.

**When NOT to reach for a macro:**

- The shape only repeats 2-3 times. Cost of macro
  abstraction > cost of duplication.
- The "same shape" actually has subtle per-call-site
  differences. Trying to parameterize them produces a
  macro that is harder to read than the original. Use a
  helper function instead.
- The macro hides control flow (early returns from inside
  the macro, branches the reader cannot see at the call
  site). Macros that hide control flow surprise readers
  and trip them on review.

**Process docs.** When designing a new module, scan for the
"this pattern repeats N times" shape BEFORE writing the
first instance. If you can predict the macro from the
spec, define it first, write the N invocations second.
This is design-by-budget per
`feedback_sw_checklist_patterns` in the agent memory.

## Phase 2: start-up

What happens once per process belongs here: registry
construction, parsing argv, loading config files, opening
log sinks. The cost is paid once at boot, amortized over
the lifetime of the process.

**Patterns:**

- `OnceLock<T>::get_or_init(closure)` for thread-safe
  lazy initialization (replaces `lazy_static` in stable
  Rust). Pay the closure cost on first access; subsequent
  accesses are a single atomic load.
- Builder pattern: `Foo::builder().with_x(...).build()` so
  construction is explicit and orderly. The builder is the
  start-up code; the resulting `Foo` is what runtime code
  uses.
- Init function called from `main` (or a top-level
  framework entry point) that wires together the
  long-lived state once.
- `Arc<T>` or `Rc<T>` to share start-up state with worker
  closures without rebuilding it.

**Example in this repo.** `mlpl-runtime::call_builtin`
dispatches by walking per-module `NAMES` constants. Those
constants are compile-time. The dispatch itself is a
straight-line match -- no per-call initialization.

**Anti-pattern:** repeating start-up work inside a hot
loop. If a function builds a `HashMap` on every call, hoist
to a `OnceLock` or pass the map in as an argument from the
caller.

## Phase 3: conditional

Branches taken based on a flag or feature -- selecting an
implementation, not transforming data. The branch happens
once per call, not per item.

**Patterns:**

- `#[cfg(feature = "X")]` and `#[cfg(target_arch = "...")]`
  for build-time conditionals. The compiler eliminates the
  unselected code; no runtime cost. Use this for: WASM vs
  native, optional integrations (`image-io`, `mlx`),
  test-only helpers.
- `Box<dyn Trait>` or generic parameters for runtime
  polymorphism. The dispatch table is set up at start-up;
  per-call cost is one indirect jump.
- A small `enum` + `match` for a closed set of choices. The
  compiler can inline arms; cost is one branch.
- Trait dispatch via methods on a configured struct: the
  struct is set up at start-up, the trait method is the
  per-call branch.

**Example in this repo.** `device("mlx") { body }` selects
the MLX runtime backend at start-up; inside the block, no
runtime "am I in MLX mode" check exists -- the dispatch
function pointer was set up when the block was entered.

**Anti-pattern:** an `if config.feature_x { ... } else { ...
}` check that runs on every iteration of a hot loop. Hoist
the choice ABOVE the loop and dispatch once.

## Phase 4: dataflow pipeline

Per-item transformation: stream of inputs in, stream of
outputs out. Each item flows through a sequence of stages.
This is the largest source of "wide function" mistakes
because programmers write nested loops instead of pipelines.

**Patterns:**

- Iterator combinator chains:
  ```rust
  input
      .iter()
      .filter(is_valid)
      .map(parse_entry)
      .map(normalize)
      .collect::<Vec<_>>()
  ```
  Each closure is a stage. Each stage is a small named
  function. The chain reads top-to-bottom like a sentence.
- `Result::and_then` and `Option::map_or_else` for
  fallible-stage chains. Each stage produces a `Result` or
  `Option`; the chain composes them without intermediate
  match statements.
- `fold` for stateful reductions (sum, max, accumulator).
- `flat_map` for nested iteration without nested `for`.
- `scan` for stateful per-item transforms.
- `try_fold` for early-exit reductions.

**Key rule: define stages separately from composition.**
The outer function is the *recipe* (which stages, in what
order). The stages themselves are *ingredients* (small
named helpers). When you read the outer function, you read
the recipe; you do not need to inline the ingredient
definitions.

**Example.** Refactoring a 27-line `decode_directory_to_record`:

```rust
// Bad: 27 lines in one function, four jobs interleaved.
fn decode_directory_to_record(dir: &Path, h: usize, w: usize) -> ... {
    // walk dir, filter images, decode each, build X/Y/names
    let mut paths = ...;
    for entry in fs::read_dir(dir)? { ... }
    paths.sort();
    if paths.is_empty() { return Err(...); }
    let mut x_data = Vec::new();
    let mut y_data = Vec::new();
    let mut names = Vec::new();
    for path in &paths {
        x_data.extend_from_slice(&decode_and_resize(path, h, w)?);
        let name = ...;
        y_data.push(label_for(name) as f64);
        names.push(name.to_string());
    }
    build_record(...)
}
```

```rust
// Good: orchestrator reads as recipe, stages are leaves.
fn decode_directory_to_record(dir: &Path, h: usize, w: usize) -> ... {
    let paths = sorted_image_paths(dir)?;
    if paths.is_empty() { return Err(empty_dir_err(dir)); }
    let (x_data, y_data, names) = decode_paths(&paths, h, w)?;
    build_record(paths.len(), 3, h, w, x_data, y_data, names)
}

fn sorted_image_paths(dir: &Path) -> Result<Vec<PathBuf>, EvalError> { ... }
fn decode_paths(paths: &[PathBuf], h: usize, w: usize)
    -> Result<(Vec<f64>, Vec<f64>, Vec<String>), EvalError>
{
    paths
        .iter()
        .map(|p| decode_one(p, h, w))
        .collect::<Result<Vec<_>, _>>()?
        .into_iter()
        .unzip3()  // or fold into three Vecs
}
fn decode_one(path: &Path, h: usize, w: usize)
    -> Result<([f64; ...], f64, String), EvalError> { ... }
```

The orchestrator is 5 lines. Each helper is its own
short, named operation. Errors propagate via `?`. The
data flow is left-to-right through the iterator chain.

**Anti-pattern:** stateful loops with `let mut`
accumulators when an iterator combinator would do the
same job in one line.

## Building chains vs dispatching chains

A function that **builds** a value (an `Environment`, a
`ModelSpec`, a parser AST) is a *constructor* or *builder*.
A function that **dispatches** a value to one of N
implementations (the eval engine, the runtime registry,
the model-apply path) is a *router*. These are two
different concerns. **Do not put both in the same
function**, and prefer not to put both in the same module.

**Why this matters.** A "build + dispatch" function is
roughly twice as wide as either half on its own. It also
has twice as many reasons to change: a new builder pattern
forces a rewrite even though the dispatch is unchanged,
and vice versa.

**Signs you're mixing them:** the function name has
"build" or "construct" in the docs but the body has a
`match` over node kinds. Or the body starts with field
allocation and ends with a registry lookup. Split.

**Example in this repo.** Saga 32 step 002 split
`mlpl-runtime` into:

- `mlpl-runtime` (the dispatcher: `call_builtin` walks
  per-module `NAMES` constants and routes to the matching
  `try_call`).
- `mlpl-runtime-{math, data, dim-reduction}` (the
  per-family builtin bodies -- each one builds and returns
  a result).

The dispatcher reads as one function; each builder family
has its own crate with its own module organization. The
parts evolve independently.

## One responsibility per function

If you cannot name what a function does in five words
without "and", split it. The split usually clarifies the
OG function's name too.

**Test:**

- "parses input and validates and computes" -> three
  functions: `parse_input`, `validate_input`,
  `compute_result`.
- "loads dataset and builds record and writes to disk" ->
  three functions plus an orchestrator that calls them in
  order.

**Counter-test:**

- "evaluates an expression to a value" -- one
  responsibility, even if 24 lines.
- "renders a Lesson struct to HTML" -- one
  responsibility, even if it uses three different yew
  components inline.

If the function name needs an "and", the split is real.

## Build-time code generation (a fifth phase: pre-compile)

`build.rs` runs BEFORE the main compile. It can read
external data (config files, schema definitions, builtin
specs) and write Rust source into `$OUT_DIR`, which the
main source pulls in via `include!()`. Combined with
macros, this becomes a powerful "one source of truth ->
many derived artifacts" pattern:

1. **External data**: a `builtins.yaml`, `demos.toml`,
   `tokens.csv`, or similar single-source-of-truth file.
2. **`build.rs`**: parses the data, emits a generated
   `.rs` file. The generated file is typically a sequence
   of macro invocations, since macros are the most
   compact way to express the resulting structure.
3. **A `define_X!` macro**: declared in the consuming
   crate's source. The macro expands one invocation
   line into:
   - An entry in the dispatch table (per-call phase
     code).
   - An entry in a `:help`/docs table (compile-time data).
   - The body of the corresponding function (domain
     logic).
   - The route registration (start-up wiring).
4. **Source**: `include!(concat!(env!("OUT_DIR"),
   "/generated.rs"));` pulls the generated file in.

The macro definition lives in ONE place. The data file
lives in ONE place. Everything else (init code, dispatch
code, domain logic, docs) is regenerated from those two
sources every build. Adding a new entry to the system =
adding one row to the data file. No drift between the
dispatch table and the docs table, ever, because both
fall out of the same macro expansion.

**Real-world examples of this pattern:**

- `prost`: build.rs reads `.proto` files, generates Rust
  structs + serializers via macros.
- `phf` (perfect hash function): build.rs computes a
  compile-time-known hash for a keyset, emits a
  zero-runtime-cost lookup.
- Many embedded crates: build.rs reads device descriptors,
  generates register definitions + accessor methods.

**Trade-offs:**

- Cost: build.rs adds a step to every `cargo build`. The
  step is fast for small data sources, slow for large ones.
  IDE features (rust-analyzer go-to-definition,
  autocomplete) sometimes struggle with the generated
  file.
- Payoff: one source of truth; the cost-per-new-entry is
  literally one row in the data file. Five tables stay
  in sync by construction.
- When to reach for it: when you have a registry with
  >= 10 entries each of which needs to appear in 3+
  places (dispatch, docs, autocomplete, completeness
  test). Below that threshold, the macro-without-build.rs
  pattern is enough.

**The four phases this enables:**

| Phase | What the codegen produces |
|-------|---------------------------|
| Compile time | `const` tables (e.g. `BUILTIN_GROUPS`), help-text strings, doc anchors |
| Start-up | `register_X(...)` calls compiled into init code, dispatcher tables populated once |
| Conditional | `#[cfg]`-gated alternative impls of the same entry |
| Dataflow | Per-call bodies of dispatched functions (the actual domain logic) |

A single macro invocation generated by build.rs can
produce code for all four. That is the most line-cheap
arrangement Rust offers: one row of data -> one macro
expansion -> code at every phase.

**Where the project does not use this yet but could:**

- `mlpl-runtime`'s builtin registry is hand-maintained
  across `BUILTINS`, the per-family `NAMES` arrays, the
  per-builtin dispatch match arms, and the
  `:builtins`/`:describe` tables. A single
  `builtins.yaml` + `define_builtin!` macro driven by
  `build.rs` would collapse all four into one row per
  builtin. Carry-over candidate for a future tech-debt
  saga.

## Functional composition: the compact style

Functional Rust is compact Rust. The iterator combinator
chain and the monadic `Result`/`Option` chain together
replace 80% of what an imperative loop or a nested
`if let Ok(...) = ...` ladder would write. They also pay
testability dividends (pure stages are trivial to test in
isolation) and compose into pipelines that read top-down.

**Iterator pipelines.** Already covered under Phase 4, but
the punchline is worth repeating: `.iter().filter().map()
.collect()` is the right shape for any "transform a
collection of inputs into a collection of outputs." Each
stage is a small named helper. The chain is the
orchestrator.

**Result and Option chains.** When the work is fallible at
each step, `?` operator + `Result::and_then` /
`Option::and_then` compose stages without nested matches.
Example:

```rust
fn classify(raw: &str) -> Result<Label, EvalError> {
    let parsed = to_number(raw)?;        // stage 1: parse
    let normalized = normalize(parsed)?; // stage 2: normalize
    let label = pick_label(normalized);  // stage 3: dispatch
    Ok(label)
}
```

vs the imperative equivalent:

```rust
fn classify(raw: &str) -> Result<Label, EvalError> {
    let parsed = match to_number(raw) {
        Ok(p) => p,
        Err(e) => return Err(e),
    };
    let normalized = match normalize(parsed) {
        Ok(n) => n,
        Err(e) => return Err(e),
    };
    let label = pick_label(normalized);
    Ok(label)
}
```

The `?`-chained version is 3 statements (orchestrator: one
per stage) vs ~10. Same correctness.

**From / Into for implicit conversions.** When stage A
produces a `RawValue` and stage B needs an `Item`, an
`impl From<RawValue> for Item` makes the pipeline read
`raw.into()` instead of `convert_raw(raw)`. The conversion
logic lives ONCE in the trait impl; every call site is one
token.

**Closures as first-class values.** Pass `|x| x.field + 1`
to `map` instead of writing a one-shot helper. Hoist the
closure to a named fn when the body grows past 3-5 lines
or repeats at multiple sites.

**Pure functions are testable.** A pure stage (`fn
parse_entry(line: &str) -> Result<Entry, ParseError>`)
takes input, returns output, no side effects. Tests are
1-3 lines each. The orchestrator that wires stages
together is also testable (call it with synthetic
inputs, inspect the chain's output). Functional style
collapses the "test setup + teardown" tax that imperative
code with state pays per test.

**Patterns:**

- `?` for early-exit fallible chains.
- `map_or_else(default, transform)` instead of
  `if let Some(x) = opt { transform(x) } else { default() }`.
- `unwrap_or_else(|| ...)` instead of `if let Some(...)
  { ... } else { ... }` returning a value.
- `collect::<Result<Vec<_>, _>>()` to turn an iterator of
  `Result`s into a `Result<Vec<...>, ...>`.
- `try_fold` for stateful reductions that can fail.
- `flat_map` for nested iteration without `for` blocks.

**Anti-patterns:**

- Building a `Vec` with `let mut acc = Vec::new(); for x
  in xs { acc.push(transform(x)); }` instead of
  `xs.iter().map(transform).collect()`.
- A `match` whose arms each return early after a
  one-statement transform: this is `map_or_else` in
  disguise.

## Type-level techniques

Encode invariants in the type system so the compiler
catches violations and the runtime checks become
unnecessary. Each technique below is small per use and
removes runtime branches.

### Newtype pattern

Wrap a primitive in a one-field tuple struct to give it
domain meaning and prevent mix-ups:

```rust
pub struct ParamName(String);
pub struct VarName(String);

// Now `fn set_param(name: ParamName, ...)` and
// `fn set_var(name: VarName, ...)` cannot be called with
// each other's arguments. The compiler enforces the
// distinction; no runtime check.
```

Cost: one type definition + a constructor. Payoff: every
call site is line-cheap (`set_param(ParamName(name))`),
and bugs that would have been runtime panics are now
build errors.

### Phantom types for state machines

When a struct has lifecycle states (Open, Closed,
Validated, Errored), encode each state in a phantom type
parameter:

```rust
pub struct Session<S> { _state: PhantomData<S>, ... }
pub struct Open;
pub struct Closed;

impl Session<Open> { fn close(self) -> Session<Closed> { ... } }
impl Session<Closed> { fn reopen(self) -> Session<Open> { ... } }
```

Calling `close()` on a `Session<Closed>` is a build error.
The runtime never needs an `is_open` flag check; the type
system is the check.

### Const generics

When a function operates on a `[T; N]` array of
compile-time-known size, use a const generic parameter
instead of `&[T]`. The compiler specializes per N; bounds
checks disappear.

```rust
pub fn dot<const N: usize>(a: &[f64; N], b: &[f64; N]) -> f64 {
    let mut s = 0.0;
    for i in 0..N { s += a[i] * b[i]; }
    s
}
```

The for-loop bounds are unrolled or eliminated by the
compiler.

### Sum types (enums) + exhaustive match

Rust's `enum` + `match` enforces that every case is
handled. Adding a new variant breaks the build at every
`match` that did not get updated -- which is the desired
behavior. This is the same compile-time-check vs
runtime-check trade as newtype/phantom.

The project's `Value::{Array, Str, StrList, Result,
Record, Model, ...}` is exactly this pattern.

## Patterns for repeated boilerplate

When the same shape repeats at many sites, the cost per
site dominates. Push the shape into one definition.

### Trait + blanket impl

Define behavior once for any type that satisfies a bound:

```rust
trait Describe { fn describe(&self) -> String; }
impl<T: Display> Describe for T { fn describe(&self) -> String { format!("{self}") } }
```

Now every `Display` type has `.describe()` without
per-type impls. The blanket impl is the macro-equivalent
for type-level dispatch.

### Builder pattern

Replace a constructor with many optional fields by a
chain of `.with_*()` methods returning `self`:

```rust
let cfg = Config::builder()
    .with_seed(42)
    .with_data_dir("/tmp")
    .build();
```

Each method is a one-liner. The user opts into fields
they care about; defaults handle the rest.

### Visitor pattern

When walking a recursive structure (an AST, a tree, a
model spec), define a trait with one method per node
kind; pass an implementor through the walk. New behaviors
are new implementors -- you do not touch the walk code.

```rust
trait NodeVisitor {
    fn visit_linear(&mut self, w: &str, b: &str);
    fn visit_chain(&mut self, children: &[ModelSpec]);
    // ...
}

fn walk(spec: &ModelSpec, v: &mut dyn NodeVisitor) {
    match spec {
        ModelSpec::Linear { w, b } => v.visit_linear(w, b),
        ModelSpec::Chain(c) => { v.visit_chain(c); for ch in c { walk(ch, v); } }
        // ...
    }
}
```

A new "count params" walk is one new impl; the walk
function is unchanged. A new "render to string" walk is
another. Each impl is small.

### Delegation via composition

When a wrapper type forwards most methods to an inner
field, `Deref` or explicit delegation methods keep the
wrapper thin:

```rust
pub struct CachedSession { inner: Session, cache: HashMap<_, _> }

impl std::ops::Deref for CachedSession {
    type Target = Session;
    fn deref(&self) -> &Session { &self.inner }
}
```

`CachedSession` now exposes every `&self` method on
`Session` for free. Only the cache-specific methods need
their own bodies.

## Strict dependency DAG

The crate-level and module-level dependency graphs must be
**acyclic**. A cycle is structural debt: it forces
unrelated changes to ship together, blocks crate splits,
and forces the build to recompile both sides of the cycle
together every time either side changes.

When a refactor reveals a cycle, **break the cycle**, do
not defer it. Two techniques:

1. **Trait-callback inversion.** Define a trait in the
   lower crate that the higher crate implements. The lower
   crate takes `&mut dyn Trait` and calls back without
   importing the upper crate's concrete types.
2. **Shim split.** Each cyclic function splits in two: a
   pure half (no callback) in the lower crate, and a
   wrapper half (resolves args, calls the pure half) in
   the higher crate.

See [feedback_no_cyclic_deps.md] in the agent memory for
the specific saga-32 cycle-breaking story.

## Anti-patterns (do NOT do these)

- `#[rustfmt::skip]` to keep wide struct literals on one
  line. The formatter is on the side of the next reader.
  If a struct literal is too wide for one line, the struct
  has too many fields. Split it.
- `#[allow(clippy::too_many_arguments)]` to dodge the
  argument-count lint. Bundle related args into a struct
  (see `LinearLoraInputs`, `AttentionInputs` in this repo).
- Workspace `rustfmt.toml` overrides that widen the
  per-line budget. That globalizes a per-function hack.
- Compressing `let x = expr1; let y = expr2;` chains into
  one line. Each `let` is a thought; compressing thoughts
  hides them. The line count goes down, the comprehension
  cost goes up.
- Adding `cfg!()` runtime checks where a `#[cfg(...)]`
  build-time gate would do (the runtime check pulls the
  dead branch into the binary).
- Hand-rolled loops with `let mut` accumulators when an
  iterator chain would express the same intent.
- Inline tests that push a production module over the
  function-count budget. Move tests to a `tests/` sibling
  file or split the inline `mod tests { ... }` across the
  appropriate phase boundary.

## Symptom -> technique (sw-checklist quick lookup)

When `sw-checklist` flags a specific issue, the lookup
below maps the warning category to the technique most
likely to retire it. Walk these first before inventing a
new approach.

### Function LOC over 25 (Function-LOC warning)

| Symptom | First-try technique |
|---------|---------------------|
| Function does steps A, B, C inline | Extract each into a named helper; orchestrator becomes 3 lines (top-down delegation). |
| Function has 2-3 nested loops | Replace with iterator pipeline (`.iter().map().filter().fold()`); each stage is a small named helper. |
| Function has 4+ `match` arms, each 10+ lines | Each arm becomes a named helper; the match becomes a dispatch. (Building-chains-vs-dispatching-chains.) |
| Function has 6+ argument-count / type checks at the top | Hoist into a macro (`check_arity!`, `check_kind!`); per-fn becomes one line. |
| Function builds a struct with 5+ fields | Builder pattern, or pre-build field values in let-bindings then construct in one line. |
| Function mixes parsing + validation + emission | Split by responsibility into `parse_*`, `validate_*`, `emit_*`; orchestrator chains them. |
| Function has `let mut` accumulator + push loop | `.iter().map(...).collect()` |
| Function has nested `match` on `Result`/`Option` | `?` operator + `and_then` chain. |

### Function LOC over 50 (Function-LOC FAIL)

Same techniques as above, just more of them. The
function is doing 3-4 things instead of 2. Walk the four
phases (compile-time / start-up / conditional / dataflow)
and identify which pieces belong where.

### Module function count over 7 (Module-Function-Count FAIL)

| Symptom | First-try technique |
|---------|---------------------|
| Several `impl Self` methods cluster by responsibility (data ops + render ops + validate ops) | Each cluster moves to a sibling `impl Self` block in its own file. Same struct, multiple `impl` blocks across files. |
| Same boilerplate-shaped fn repeats N times | Macro it; the per-fn definitions disappear into the macro expansion. |
| Production fns + test fns + test helpers in same file | Move tests + helpers to a sibling `mod.rs` / `tests/` file; production fn count drops by the test count. |
| One big dispatcher with N arm-handler fns | Split dispatcher into one file, arm handlers into a sibling file. |

### File LOC over 500 (File-LOC FAIL)

| Symptom | First-try technique |
|---------|---------------------|
| Pure data (static tables, lessons, demos) | Split by topic into sibling files (each holds one topical const). The "facade" file references them. |
| One struct with 20+ methods | Split methods into multiple `impl` blocks across sibling files. |
| Dispatcher + arm handlers in one file | Extract arm handlers to a sibling file. |
| Same module hosts builders + dispatchers + tests | Pull each phase to its own file (builders.rs, dispatch.rs, tests/). |

### Crate module count over 7 (Crate-Module-Count FAIL)

| Symptom | First-try technique |
|---------|---------------------|
| Many topically-different modules in one crate | Pull a topical cluster (5+ related modules) into a new sibling crate. Old crate becomes a facade depending on the new one. |
| Modules that group naturally already (`foo_a`, `foo_b`, `foo_c`) | New crate `mlpl-foo` absorbs them; the parent crate re-exports. |

### Clippy Allows attribute (Clippy-Allows FAIL)

The lint exists for a reason. Refactor the code to satisfy
it; never silence it with `#[allow(clippy::...)]` outside
vendored code.

| Clippy lint | Refactor |
|-------------|----------|
| `too_many_arguments` | Bundle related args into a struct. (See `LinearLoraInputs`, `AttentionInputs` in this repo.) |
| `result_large_err` | Box the large variant: `BreakSignal(Box<Value>)` instead of `BreakSignal(Value)`. |
| `excessive_precision` | Round the constant to ~7 significant digits. |
| `type_complexity` | Define a type alias for the complex tuple/closure. |
| `module_inception` | Rename the inner module or pull it up one level. |
| `approx_constant` | Use `std::f64::consts::PI` etc. |

## sw-checklist issue avoidance (design phase)

The cheapest retirement is the warning that never
existed. When writing new code, design with the budgets
in mind:

1. **Budget per function first.** Before writing a
   function, jot down its three parts (input/processing/
   output). If the body of any part will be > 15-20 lines,
   it's a sub-function, not a section. Name it now.
2. **Budget per module.** A new module gets a name that
   identifies its responsibility (`parse.rs`,
   `validate.rs`, `dispatch.rs`). If you can't name it in
   one word, the responsibility is too broad. Split.
3. **Budget per crate.** A new crate gets a topical name
   (`mlpl-eval-data`, `mlpl-runtime-dim-reduction`). When
   the crate's module list exceeds 5, ask whether two
   topics live here when they should be in separate
   crates.
4. **Look for repetition early.** When you find yourself
   typing the same shape a third time, stop and macro it
   (or hoist to a helper, or pull into a builder).
5. **Choose the phase upfront.** New code goes into the
   phase that fits: `const` for data, init function for
   start-up, `#[cfg]` for compile-time conditionals,
   iterator pipeline for per-item work. Mixing phases is
   the most common reason a function later trips the
   25-LOC warning.

The agent memory entry
`feedback_sw_checklist_patterns.md` codifies this as
"design for sw-checklist budgets up front -- extract
helpers + struct args before writing, not after the
linter yells."

## sw-checklist issue correction (existing code)

When `sw-checklist` flags an existing function, follow
this algorithm:

1. **Read the function.** Identify what it does in one
   sentence. If the sentence has "and", split the
   function.
2. **Walk the four phases.** Is some piece compile-time?
   Hoist to `const`. Is some piece start-up? Pull to a
   builder or init function. Is some piece a conditional
   selecting an implementation? Replace with `#[cfg]` or
   trait dispatch. Is the rest per-item? Confirm it
   reads as a pipeline.
3. **Apply the technique from the symptom table.** Each
   row tells you the first thing to try.
4. **Re-run sw-checklist.** Confirm the issue retired and
   no new issues introduced. If a new issue appeared, the
   split was wrong -- back up and try a different split.
5. **Verify the dep graph is still a DAG.** New sibling
   files should depend strictly downward; no upward
   imports.
6. **Run the full quality gate.** Tests + clippy + fmt
   green.

The strict per-step rule (net-negative on BOTH fails AND
warnings vs HEAD~1) keeps each commit honest about
progress.

## When stuck: look for the phase mismatch

A function over budget that resists splitting usually has a
**phase mismatch**: it is doing per-call work that belongs
at start-up, or per-item work that belongs at compile time,
or vice versa. Walk the four phases (compile time, start-up,
conditional, dataflow) and ask which phase each piece of
the function's work actually belongs in. Move each piece
to its phase. The function will shrink, often dramatically.

A pure dataflow function over budget probably needs to be
split into multiple stages, each its own helper. A pure
start-up function over budget probably needs a builder
pattern. A mixed-phase function needs to be split by phase
first; the per-phase pieces are usually small enough.
