Recommendation

Your ordering is mostly right, but I would adjust it to:

Function composition
General broadcasting
Function-taking map, reduce, and scan
A BQN-like table/outer-product combinator
List/tensor comprehensions
Cell/rank-based mapping
Broader shape algebra

The key architectural point is that composition plus higher-order array combinators gives more leverage than comprehensions. Comprehensions improve notation; map, reduce, scan, and table improve the language’s computational model and compiler opportunities.

Also, a correction to my previous comparison: BQN does not use full NumPy-style trailing-axis broadcasting. It primarily uses scalar extension and its own leading-axis agreement rules. BQN’s Each, Table, Cells, and Rank make the intended mapping behavior explicit.

sw-MLPL already has scalar broadcasting, reshape, transpose, axis reductions, named axes, loops over rows, and substantial tensor/ML machinery, so the next step should extend those existing semantics rather than introduce a separate array-programming subsystem.

1. Broadcasting: the right short-term feature

sw-MLPL already supports:

[1, 2, 3] * 10

The natural extension is compatible-shape broadcasting:

X = reshape(iota(6), [2, 3])
bias = [10, 20, 30]

X + bias
# [10, 21, 32]
# [13, 24, 35]

This is immediately useful for:

bias addition;
normalization;
masks;
per-feature scaling;
batched loss calculations;
attention score manipulation;
activation parameters;
dataset preprocessing.

Broadcasting can avoid physically copying expanded values and can expose vectorizable computation to the backend. That is why it is central to NumPy and the Array API model.

Recommended rules

I would use conventional trailing-dimension broadcasting for unnamed axes:

[2, 3] + [3]       -> [2, 3]
[4, 1, 8] + [7, 8] -> [4, 7, 8]
[2, 3] + [2]       -> error

For each aligned dimension:

a == b, or
a == 1, or
b == 1

Missing leading dimensions behave as dimensions of size one.

That is familiar, predictable, and compatible with ML users’ expectations.

Named-axis broadcasting

sw-MLPL’s named axes offer something more valuable than simply copying NumPy:

X : [batch, token, feature] = ...
bias : [feature] = ...

Y = X + bias

Here, feature should align by name, not merely by position.

Likewise:

mask : [batch, token] = ...
scores : [batch, head, token] = ...

should either align semantically or fail with a precise diagnostic. Named dimensions already propagate through operations and produce structured shape mismatch errors, so broadcasting should build on that machinery.

I would use this policy:

Operands	Alignment
Neither has labels	Trailing positional broadcasting
Both fully labeled	Match axes by label
One labeled, one scalar	Always valid
One labeled, one unlabeled vector/tensor	Require explicit alignment or a narrowly defined rule
Labels conflict	Error

The dangerous case is silently aligning an unlabeled [768] tensor to the wrong axis of a labeled tensor. Explicitness is preferable there:

broadcast_to(bias, [feature])

or perhaps:

bias : [feature]

before the operation.

Implementation boundary

Broadcasting should initially apply only to element-wise operations:

+ - * /
comparisons
min/max
logical operations
unary/binary element-wise math

It should not initially alter:

matmul
reshape
concat
reductions
indexing

That keeps the semantic change local and testable.

2. Generalized map: immediately after composition

Once u:fn values can be composed and passed around, map stops being merely a loop convenience and becomes a central language operator.

Possible surface syntax:

normalize = u:center |> u:scale
ys = map(normalize, xs)

Or, depending on your composition syntax:

ys = map(u:center >> u:scale, xs)

The first version of generalized map should remain simple:

map(u:square, [1, 2, 3])
map(u:normalize, rows(X))

The important design question is what unit is mapped.

A flat map(fn, X) could mean one of three things:

map over every scalar element;
map over major cells—rows for a matrix;
map over an explicitly named axis.

Those should not be conflated.

Suggested API
map(u:fn, X)                   # scalar elements
map_axis(u:fn, X, "batch")     # slices selected by axis
map_rows(u:fn, X)              # convenience alias, perhaps library-level

Later:

map_cells(u:fn, X, rank)

BQN distinguishes these operations deliberately:

Each maps over elements;
Cells maps over major cells;
Rank generalizes mapping to cells of a chosen rank;
Table applies a function to every pair of elements.

That separation is worth adopting semantically, even without adopting BQN glyphs.

3. Generalized reduce and scan may be more important than comprehensions

Once functions are values, these become natural:

reduce(u:add, X)
reduce(u:max, X, "feature")
scan(u:add, tokens)

sw-MLPL already has named reductions such as:

reduce_add(X, "feat")

A generalized reducer could coexist initially:

reduce(u:add, X, "feat")

Then built-ins become optimizable specializations rather than unrelated language features:

reduce_add(X, axis)
≈ reduce(u:add, X, axis)
Why scan matters for MLPL

scan deserves early consideration because it supports:

cumulative sums and products;
running statistics;
token positions;
recurrence experiments;
state-space models;
discounted returns;
prefix computations;
segmented sequence processing;
some parallel algorithms.

A comprehension can express a loop, but it does not naturally express that each output depends on the previous accumulated state. scan does.

I would therefore put:

map → reduce → scan

before comprehensions.

4. BQN’s Table is a strong fit

BQN’s Table applies a binary function to every combination of elements from two arrays. For vectors of lengths m and n, the result is an m × n array; for higher-rank inputs, the result shape is the concatenation of their shapes.

In readable sw-MLPL form:

table(u:add, [1, 2, 3], [10, 20])

producing:

11 21
12 22
13 23

Or:

distances = table(u:distance, points_a, points_b)

This is directly useful for:

pairwise distances;
similarity matrices;
Cartesian parameter combinations;
kernels;
attention experiments;
confusion matrices;
grid generation;
clustering;
exhaustive comparisons.

Potential names:

table(u:f, A, B)
outer(u:f, A, B)
cross_map(u:f, A, B)

I prefer table because outer is commonly associated specifically with outer products and may misleadingly suggest multiplication. But outer will be more immediately familiar to NumPy/JAX users.

This feature becomes especially elegant with composition:

distance = u:subtract |> u:square |> u:reduce_add |> u:sqrt
D = table(distance, A, B)

The exact composition must accommodate binary-to-unary transitions, but conceptually this is a very natural MLPL use case.

5. List comprehensions: useful, but not really the main BQN lesson

List comprehensions are not especially characteristic of BQN. BQN usually handles these problems using array operations, mapping modifiers, masks, and selection rather than Python-style comprehensions. Its more distinctive contributions are the explicit distinctions among Each, Table, Cells, Rank, composition, and structural transformations.

Comprehensions still fit sw-MLPL because the language already has:

for row in X {
    ...
}

A producing form would naturally extend that:

squares = [x * x for x in xs]
positives = [x for x in xs if x > 0]

For tensors:

normalized = [normalize(row) for row in rows(X)]
Benefits
Familiar to Python and Rust users.
Easy to teach.
Clear for filtering and irregular data production.
Natural extension of existing for.
Useful before a full rank/cell model exists.
Can lower to existing loops initially.
Risks
It can create a second array model

These two forms may appear equivalent:

map(u:square, X)
[x * x for x in X]

But they may differ in:

whether X iterates scalars or rows;
output shape inference;
autograd behavior;
backend fusion;
device placement;
handling variable-shaped results.

Those differences need explicit specification.

It encourages scalar thinking

For ML workloads, this:

[x + bias for x in X]

may be less optimizable and less expressive than:

X + bias

Comprehensions should be the escape hatch for transformations that do not fit direct array algebra, not the preferred form for every operation.

Filtering changes shape dynamically
[x for x in X if predicate(x)]

cannot generally preserve a static tensor shape. It should likely produce a list or rank-1 dynamic array, not an arbitrary dense tensor.

That distinction becomes important for MLX, CUDA, compilation, and autograd.

Recommended staged comprehension design
Stage 1: list-producing comprehensions
[x * x for x in xs]
[f(x) for x in xs if p(x)]

Constraints:

iterate over a rank-1 array, dataset, or explicit row iterator;
produce a rank-1 array if all results are compatible scalars;
otherwise produce a list value, should MLPL acquire heterogeneous lists;
lower to ordinary loop semantics;
CPU/interpreter first.
Stage 2: tensor comprehensions

Later, a shape-preserving form could carry stronger guarantees:

tensor[f(x) for x in X]

or perhaps no new syntax if shape inference can prove regularity.

Tensor comprehensions can eventually become a compiler-level facility for fusion and kernel generation. There is precedent for treating mathematical tensor comprehensions as a high-level description that lowers into optimized GPU kernels, but that is a much more ambitious feature than ordinary list syntax.

6. Shape algebra: later, but lay foundations now

I agree that a broad shape algebra should come later. sw-MLPL already has enough shape operations for useful ML:

reshape
transpose
concat
named axes
axis reductions

BQN’s shape model is much more pervasive. Its reshape can flatten, reshape, truncate, cyclically repeat values, infer dimensions under several policies, and interact with other structural modifiers.

Copying all of that would complicate MLPL without immediate benefit.

However, several small shape primitives would prepare the language for later generalization:

shape(X)
rank(X)
axis_size(X, "feature")
expand_dims(X, "head")
squeeze(X, "singleton")
broadcast_to(X, [batch, token, feature])
move_axis(X, "feature", 1)

These are more valuable initially than turning reshape into a BQN-like universal structural primitive.

Named shape expressions

Eventually, MLPL could support transformations such as:

X : [batch, token, head, channel]
Y = transpose(X, [batch, head, token, channel])

and perhaps:

Y = reorder(X, [batch, head, token, channel])

This is clearer for ML than numeric permutations like:

transpose(X, [0, 2, 1, 3])

That is an area where sw-MLPL can surpass BQN for its domain: shape algebra based on semantic axis names.

7. One BQN concept worth adding earlier: Over

After ordinary composition, BQN’s Over is worth considering.

Ordinary composition means:

f(g(x))

For a binary operation, Over means:

f(g(a), g(b))

BQN distinguishes this from normal composition explicitly.

Readable MLPL examples:

equal_over(u:sort, a, b)
# equal(sort(a), sort(b))

distance_over(u:normalize, a, b)
# distance(normalize(a), normalize(b))

A generic syntax might be:

u:equal over u:sort
u:distance over u:normalize

This is useful for:

comparing normalized vectors;
measuring distance after projection;
comparing canonicalized shapes;
applying the same preprocessing to two model inputs;
comparing tokenized or embedded forms.

It is compact but still understandable. I would add it only after plain unary composition is settled, because binary arity rules can otherwise become confusing.

Proposed milestones
Milestone A — Composition foundation

Implement:

first-class u:fns
unary composition
arity metadata/checking
composed-function introspection
interpreter/compiler parity

The introspection should remain readable:

u:center |> u:scale |> u:clip

rather than becoming an opaque generated closure.

Milestone B — Broadcasting

Implement:

scalar broadcasting, already present
singleton positional broadcasting
named-axis broadcasting
broadcast shape inference
zero-copy broadcast views where feasible
autograd reduction across expanded axes
structured mismatch diagnostics

The autograd point is important. If [feature] is broadcast across [batch, feature], its gradient must reduce across batch.

Milestone C — Higher-order arrays

Implement:

map(u:f, X)
reduce(u:f, X)
reduce(u:f, X, axis)
scan(u:f, X)
table(u:f, A, B)

Initially require built-in or pure u:fn operands where necessary for compiled/backend execution.

Milestone D — Comprehensions

Implement:

[f(x) for x in xs]
[f(x) for x in xs if predicate(x)]
[f(row) for row in rows(X)]

Lower them to the existing loop representation. Do not initially promise GPU fusion or static tensor output for filtered comprehensions.

Milestone E — Cells and shape operations

Implement:

map_axis(u:f, X, axis)
map_cells(u:f, X, rank)
expand_dims
squeeze
move_axis
broadcast_to

Named-axis map_axis should probably precede numeric rank because it better matches MLPL’s existing strengths.

Final prioritization
Feature	Value to MLPL	Complexity	Timing
General broadcasting	Very high	Moderate	Immediately after composition
Generic map	Very high	Moderate	Immediately after broadcasting
Generic reduce	Very high	Moderate	Same milestone as map
scan	High	Moderate	Shortly after reduce
table/outer map	High	Low–moderate	Early
List comprehensions	Medium–high	Moderate	Middle
Over composition	Medium	Low–moderate	After arity semantics stabilize
Named-axis mapping	High	Moderate–high	Middle
Rank/cell mapping	Medium–high	High	Later
Full shape algebra	High eventually	High	Later

So I would refine your conclusion to:

Broadcasting is the best near-term array feature. Generalized map/reduce/scan should follow composition and probably precede list comprehensions. Comprehensions are a useful ergonomic bridge, while named-axis mapping and shape algebra are the deeper later-stage design.

The particularly distinctive sw-MLPL opportunity is not merely BQN-style rank polymorphism. It is function composition combined with named-axis polymorphism:

normalize_features = u:center |> u:scale
Y = map_axis(normalize_features, X, "feature")

That remains readable, maps directly to ML concepts, and can eventually provide much of BQN’s compositional power without adopting its terse notation.

A good feature-selection test
A feature should probably enter sw-MLPL only when it does at least three of these:

Makes an ML building block easier to express.

Makes data flow or shape changes easier to understand.

Composes cleanly with u:fn.

Removes boilerplate without hiding important behavior.

Has one clear primary meaning.

Can be explained with a small example.

Produces useful diagnostics when misused.

Can be implemented correctly in Rust without runtime magic.

Works in both teaching examples and nontrivial programs.

Avoids creating a second competing way to express the same idea.

That last item matters most. Multiple paradigms are fine; multiple unrelated semantics for the same operation are not.

Words instead of glyphs
Using words is not merely a cosmetic substitution.

It changes the teaching model.

Compare:

f¨x
with:

each(u:f, x)
The second form exposes three concepts:

each is an operation;

u:f is a function value;

x is the data being transformed.

Likewise:

table(u:distance, points_a, points_b)
is readable before the learner knows the formal term “outer product.”

Words also make idioms searchable, documentable, and diagnosable:

error: table expects a binary function, but u:normalize accepts one argument
That is much harder to communicate cleanly around symbolic modifiers.

Terseness through idioms
Your distinction is important:

Terseness should come from reusable idioms, not compressed notation.

Good sw-MLPL terseness might look like:

or:

pairwise_distances = table(u:distance, points, points)
or:

running_loss = scan(u:add, losses)
These are short because the concepts are powerful, not because the spelling is cryptic.

That gives you semantic compression rather than visual compression.

A possible core vocabulary
I would keep the first-class functional and array vocabulary intentionally small.

Function composition
compose(u:f, u:g)
u:f |> u:g
over(u:compare, u:normalize)
Potential meanings:

compose(f, g)(x) = g(f(x))
over(f, g)(x, y) = f(g(x), g(y))
The pipe notation is readable enough to justify as syntactic sugar. The word form should remain available in documentation and introspection.

Element and collection transformation
each(u:f, values)
map_axis(u:f, tensor, "feature")
table(u:f, left, right)
I would favor each as the ordinary element-wise operation and reserve map for a more general family or perhaps omit generic map entirely.

For example:

each(u:square, values)
each_row(u:normalize, matrix)
each_axis(u:normalize, tensor, "feature")
This is more explicit than making map change meaning by rank.

Accumulation
reduce(u:add, values)
reduce_axis(u:add, tensor, "feature")
scan(u:add, values)
These reveal an important relationship:

each   transforms independent items
reduce combines items into one result
scan   combines items while retaining intermediate results
table  combines every item on the left with every item on the right
That is an excellent teaching cluster.

each, over, and table form a particularly good family
These three are worth adopting because they expose distinct patterns.

each
Apply one function independently:

squares = each(u:square, values)
Conceptually:

x₀ x₁ x₂
↓  ↓  ↓
f  f  f
↓  ↓  ↓
y₀ y₁ y₂
over
Preprocess arguments identically before a binary operation:

same_distribution =
    over(u:approximately_equal, u:normalize)
Conceptually:

left  -> normalize ┐
                    ├-> approximately_equal
right -> normalize ┘
This is useful for:

comparing normalized vectors;

comparing sorted values;

comparing projected embeddings;

measuring distances after common preprocessing.

table
Apply a binary function to every pair:

distances = table(u:distance, points_a, points_b)
Conceptually:

              points_b
            b0  b1  b2
points_a a0  f   f   f
         a1  f   f   f
That directly teaches similarity matrices, kernels, attention scores, and pairwise comparisons.

Broadcasting should remain explicit in its model
Broadcasting is useful, but it can also hide shape mistakes.

For a teaching language, the ideal is:

convenient for obvious cases;

inspectable;

conservative for ambiguous cases;

excellent diagnostics.

Example:

bias   : [feature]

The language should be able to explain:

result shape: [batch, token, feature]
Perhaps not on every execution, but through inspection:

or:

trace shapes {
    adjusted = scores + bias
}
That would fit your goal better than silently mimicking NumPy.

Likewise:

distances = table(u:distance, points, prototypes)
could be visualized as a matrix or computation grid.

This suggests that u:fn composition should retain metadata instead of immediately collapsing into an opaque closure.

A composed function might internally preserve:

enum UnaryFunction {
    Builtin(BuiltinFn),
    User(UserFnId),
    Compose(Vec<UnaryFunction>),
}
That enables:

readable diagnostics;

graph visualization;

simplification;

tracing;

teaching output;

later optimization;

serialization.

Correctness and inspectability align here.

Avoid implicit cleverness
Several ideas from the source languages should probably remain inspiration rather than direct features.

Avoid automatic tacit trains
A BQN or J programmer may infer meaning from adjacency and arity. Most learners will not.

Prefer:

average = compose(
    u:sum,
    u:divide_by_count
)
or a pipeline:

average = u:sum_and_count |> u:divide
rather than deriving hooks and forks implicitly from function placement.

Avoid excessive rank inference
Instead of making the same operator silently choose elements, rows, planes, or cells, prefer readable intent:

each(u:f, values)
each_row(u:f, matrix)
each_axis(u:f, tensor, "token")
each_cell(u:f, tensor, rank: 2)
Some aliases can lower to a common implementation, but the source should communicate intent.

Avoid overloaded punctuation
Punctuation is appropriate when it expresses universal structure:

u:f |> u:g
It is less appropriate when every modifier receives a distinct symbol.

Recommended near-term sequence
Given function composition is arriving soon:

1. Preserve composed-function structure
Before adding many combinators, ensure composed u:fn values retain:

arity;

input/output type information where known;

names;

source locations;

component functions;

purity/effect metadata eventually.

2. Add broadcasting
Start with element-wise operations and conservative shape rules.

Include:

broadcast_shape(a, b)
broadcast_to(x, target_shape)
even if most broadcasting is implicit. These explicit operations help teaching and debugging.

3. Add each
Keep its semantics narrow:

each(u:f, sequence)
Do not initially make it rank-polymorphic.

4. Add reduce and scan
These complete the core sequence-processing vocabulary.

5. Add table
It is simple, distinctive, and highly relevant to ML.

6. Add over
Do this once function arity and binary composition are well-defined.

7. Add comprehensions
Use them for cases where the operation is more readable as construction:

[x * x for x in values if x > 0]
Do not make them the main tensor-transformation mechanism.

8. Add named-axis forms
each_axis
reduce_axis
scan_axis
broadcast_axis
This is likely more valuable to sw-MLPL than general BQN-style numeric rank semantics.

The main design principle
A useful rule for sw-MLPL could be:

Prefer a word when it names a reusable computational idea. Prefer an idiom when several words repeatedly form a meaningful ML pattern. Add syntax only when it clarifies structure.

That gives you room to borrow widely without losing identity.

sw-MLPL can plausibly become a language where someone learns:

what mapping means;

what reduction means;

what broadcasting does;

how shapes propagate;

how functions compose;

how pairwise computations work;

how models are assembled;

how training changes state;

how inference differs from training.

That is a clearer and more valuable target than being the shortest language, the fastest language, or the most mathematically pure language.

Core principle
A useful formulation for sw-MLPL would be:

Code should be readable without mathematics, but mathematics should be recoverable from code whenever the computation has a meaningful mathematical interpretation.

That keeps the language approachable while making mathematical depth available rather than mandatory. It also gives sw-MLPL something most existing ML systems handle poorly: a synchronized view of program, equation, shape, and explanation.

#+call: mlpl-math("linear-example", view="indices")
or through an interactive command.

Generated views in Org
The same block could generate several siblings:

** Source
#+begin_src mlpl
...
#+end_src

** Result
#+RESULTS:
...

** Equation
\[
Y = XW + b
\]

** Indexed equation
\[
Y_{bo} = \sum_f X_{bf} W_{fo} + b_o
\]

** Shapes
| Value   | Shape             |
|---------+-------------------|
| input   | batch × feature   |
| weights | feature × output  |
| bias    | output            |
| output  | batch × output    |

** Explanation
The matrix multiplication reduces over the feature axis.
The bias is broadcast across the batch axis.
Org is an excellent host for these parallel views.

Testing strategy
Treat the Emacs integration as a separate component.

sw-mlpl/
  crates/
    mlpl-cli/
    mlpl-parser/
    mlpl-runtime/
    mlpl-inspect/

  editors/
    emacs/
      ob-mlpl.el
      mlpl-mode.el
      mlpl-doc.el
      tests/
Test the boundary using golden files.

For example:

testdata/
  linear.mlpl
  linear.inspect.json
  linear.math.tex
  linear.shapes.org
Then verify:

Rust emits stable semantic JSON.

Elisp converts it into expected Org/LaTeX.

Babel execution returns expected results.

export to HTML/PDF succeeds.

Benefits and risks
Benefits
Much faster path to usable literate tutorials.

No premature language syntax commitment.

Excellent HTML and PDF export.

Native LaTeX support.

Source, prose, results, and equations remain together.

Easy experimentation in Elisp.

Rust compiler remains smaller and cleaner.

Generated views can evolve independently of the language.

Risks
Documentation features may initially work only in Emacs.

Comment conventions could drift without a specification.

Elisp may accidentally duplicate compiler semantics.

Generated documents depend on CLI output stability.

Maintaining both Rust and Elisp adds another integration boundary.

Those risks are acceptable, especially since Emacs is already your normal environment.

Best architectural decision
I would implement the first version as:

ob-mlpl.el
    ↓ invokes
mlpl run/check/inspect
    ↓ returns
text or JSON
    ↓ rendered by
mlpl-doc.el
    ↓ embedded into
Org source/results/math/shape sections
Use manual equations and lightweight comments first. Add automatic extraction incrementally. Once the desired math and documentation conventions stabilize, move only the semantic pieces that clearly belong in the compiler into Rust.

That gives you a productive prototype now without locking sw-MLPL into speculative annotation syntax.
