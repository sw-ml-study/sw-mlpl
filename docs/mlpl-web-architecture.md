# mlpl-web Target Architecture

## Design principles

1. **Warning targets are the design goal.** Every module,
   function, file, and crate should be designed to the
   WARNING threshold, not the FAIL line. FAIL is the floor
   you never cross; WARNING is the ceiling you design
   under.

   | Metric | Design target | Warning | FAIL |
   |--------|--------------|---------|------|
   | fn/module | <=4 | >4 | >7 |
   | LOC/function | <=20 | >25 | >50 |
   | LOC/file | <=250 | >350 | >500 |
   | modules/crate | <=4 | >4 | >7 |

2. **Each domain concept is separately packaged.** Related
   concepts can be grouped (module or crate level), but
   each concept's aspects (config, dispatch, content,
   rendering, help text) live in their natural homes.

3. **Text in text files.** Demo descriptions, help text,
   tutorial content, glossary entries -- these are content,
   not code. They belong in text files included at build
   time via `include_str!` or generated by `build.rs`.
   Inline string literals in Rust source inflate LOC counts
   and obscure logic.

4. **General vs domain-specific.** General-purpose code
   (localStorage, dispatch patterns, state machines,
   iterator adapters) is physically separated from domain
   code (MLPL demos, ML concepts, tutorial curriculum).
   General code has no `use crate::` imports from domain
   modules.

## Current state (problems)

- **48 flat modules** in `src/`. Crate-module-count FAIL
  (max 7). No directory structure.
- **Demo content is inline Rust.** Each demo is a Rust
  `const` with string-literal fields (intro, takeaway,
  lines). This is content masquerading as code.
- **Components mix concerns.** `mode_bar` has 75 LOC
  because it builds a dropdown, a file upload widget,
  and a clear button in one function.
- **Render tree is 10 files.** Each is a thin layer but
  they could be 4 modules (shell, main, modes, callbacks).
- **Warnings treated as acceptable.** 461 warnings in the
  workspace; many are structural (modules at 5-7 fns).

## Target state

### Domain concept separation

Each domain concept becomes a sub-crate or directory-
module with <=4 sub-modules:

| Concept | Package | Aspects |
|---------|---------|---------|
| **Demos** | `content/demos/` | spec (struct), data (text files), runner (dispatch), progress (notes) |
| **Tutorials** | `content/tutorials/` | lesson data (text files), navigation, rendering |
| **Paths** | `content/paths/` | path definitions, walker UI |
| **Glossary** | `content/glossary/` | parsed entries, popup, search |
| **Diagrams** | `content/diagrams/` | diagram index, lazy-load rendering |
| **Help** | `content/help/` | help text (text file), dialog rendering |
| **Completion** | `ui/completion/` | prefix extraction, candidate matching, popup rendering |
| **Upload** | `ui/upload/` | image decode, REPL command, file picker |
| **Onboarding** | `ui/onboarding/` | splash, tour, what's-new, localStorage |
| **REPL** | `shell/repl/` | input row, history, submit pipeline |
| **Shell** | `shell/` | header, footer, mode bar, layout |

### Content externalization

Move string content out of Rust source:

```
content/
  demos/
    basics.toml       # name, intro, takeaway, lines
    attention.toml
    ...
  tutorials/
    lessons.toml      # lesson titles, intros, bodies
  help.txt            # :help output
  glossary.md         # already external (docs/glossary.md)
```

`build.rs` or `include_str!` at the call site reads these.
Demo `const` structs become generated from TOML/text.

### Module budget compliance (by construction)

Each sub-directory's `mod.rs` is a facade with 0 functions
(only `pub mod` and `pub use`). Each leaf module has <=4
functions. Each file is <=250 LOC. Each sub-directory has
<=4 child modules.

A module that would exceed 4 functions splits into two
modules by sub-concern. A function that would exceed 20
LOC delegates to helpers in the same module or a sibling.

### General-purpose extraction candidates

These modules have no MLPL-specific knowledge and could
live in a shared utility crate:

- `onboarding/storage.rs` -- localStorage read/write
- `ui/scroll.rs` -- DOM scroll-to-bottom + focus
- `ui/entry.rs` -- render a text entry with error styling
- Completion prefix extraction + candidate matching
  (the algorithm is domain-independent; the candidate
  list is domain-specific)
- Dispatcher pattern (SplashAction enum + match)

## Migration plan

This is a multi-step migration, not a single commit:

1. **Externalize demo content** to TOML/text files.
   Biggest LOC reduction (demos_*.rs are ~200 LOC each
   of pure string data).
2. **Group by directory** (content/, ui/, shell/) with
   mod.rs facades. Mechanical moves.
3. **Split over-budget modules** to meet warning targets.
4. **Extract general-purpose code** to utility modules
   with no domain imports.

Each step is its own agentrail step with a commit.
